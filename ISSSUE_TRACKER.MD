## Git foundation

Files: `src/opencobol2/git/*.py`, `src/opencobol2/services/git.py`

### 1. `stash_changes` can report success while stashing nothing — HIGH — **[verified]** — **FIXED**

Now captures the stash list's top entry before the push and compares it against the top entry after; raises `GitCommandFailedError` if they're identical (no new stash was actually created), instead of returning the pre-existing entry as if it were new. Regression test: `test_stash_changes_detects_noop_when_only_untracked_changes` in `tests/unit/test_git_stash.py`.

`src/opencobol2/services/git.py:1524-1601`

The only pre-check is `status.clean` (raises `GitNothingToStashError` if the repo has *no* changes at all — confirmed untracked files count as "not clean" via `git/status.py`'s `_parse_untracked_change`). After running `git stash push`, the method assumes success purely because `self._get_stashes(repository_root)` is non-empty, and returns `refreshed_stashes[0]` as "the new entry" — it never compares the stash list/oid before vs. after the push.

**Concrete trigger:** a repo already has one stash entry; the working tree has *only* untracked files; caller invokes `stash_changes(path)` with the default `include_untracked=False`. `status.clean` is `False` (untracked files are changes), so the guard doesn't fire. `git stash push` (no `--include-untracked`) finds nothing stashable, prints "No local changes to save," exits 0. `refreshed_stashes` is non-empty because it still contains the *pre-existing* stash — so the method returns that stale entry as if it were newly created. The untracked files are never actually stashed; the caller is told the operation succeeded. `tests/unit/test_git_stash.py` has no case combining a pre-existing stash with untracked-only changes.

### 2. `reset`/`get_history`/`revert_commit`/`cherry_pick_commit`/`get_commit_diff` build ref arguments with no `--` separator — HIGH (for `reset`) / MEDIUM (others) — **[verified for `reset` and `get_history`]** — **FIXED**

Empirically tested real `git` behavior first, since a naive fix would have broken `reset`: a **leading** `--` before a ref switches `git reset` into path-reset mode and silently no-ops instead of moving the branch pointer (confirmed live: `git reset --hard -- HEAD~1` left history unchanged), whereas a **trailing** `--` after the ref works correctly everywhere tested (`reset`, `log`, `show`, `revert`, `cherry-pick`) and closes off the ref-vs-path ambiguity without changing behavior. Fix has two parts: (1) `_require_ref_name`/`_normalize_optional_ref_name` (the latter via a new `is_free_text` flag, since it's also reused for tag/stash *messages* which legitimately can start with `-`) now reject any ref/branch/tag/commit-ish value starting with `-`, closing the actual argument-injection vector; (2) `reset`, `get_history`, `revert_commit`, `cherry_pick_commit`, and `get_commit_diff` all now append a trailing `--` after the ref as defense-in-depth. Regression tests: `test_reset_rejects_dash_prefixed_target` plus updated exact-command assertions across `tests/unit/test_git_reset_revert_cherrypick.py`, `test_git_history.py`, `test_git_diff.py`.

`src/opencobol2/services/git.py`: `reset` 1729-1736, `get_history` 1482-1495, `revert_commit` 1763-1774, `cherry_pick_commit` 1810-1821, `get_commit_diff` 1897-1903

Every other ref/name-taking command in this file (`stage_paths`, `create_branch`, `delete_branch`, `switch_branch`, `create_tag`, `delete_tag`, `add_remote`/`remove_remote`/`rename_remote`, `fetch`/`pull`/`push`) places the user-supplied value after a literal `"--"` — directly confirmed for `switch_branch` (`("switch", "--", normalized_name)`, `git.py:1264-1280`). `reset` (confirmed: `("reset", f"--{mode}", normalized_target)`, no `--`) and `get_history` (confirmed: `arguments += (normalized_ref,)`, no `--`) do not follow this pattern; nothing in `_require_ref_name`/`_normalize_optional_ref_name` rejects a leading `-`.

**Concrete trigger:** this same service's own `create_branch`/`create_tag` already allow creating a ref literally named e.g. `-force` (git itself permits this when disambiguated with `--`). Calling `reset(path, target="-force", mode="mixed")` builds `git reset --mixed -force` — an ambiguous, unpredictable invocation for a destructive operation. Calling `get_history(path, ref="-force")` builds `git log --format=... -force`, which git rejects as an unrecognized option instead of showing that ref's history.

### 3. `revert_commit`/`cherry_pick_commit` cannot target a merge commit — MEDIUM — **[confirmed]** — **FIXED**

Both now accept an optional `mainline: int | None` parameter that adds `-m <n>` to the git invocation when given. Regression tests: `test_revert_commit_with_mainline_verifies_exact_git_command`, `test_cherry_pick_commit_with_mainline_verifies_exact_git_command`.

`src/opencobol2/services/git.py:1746-1791`, `1793-1838`

Neither exposes git's `-m/--mainline <parent-number>` option, so reverting/cherry-picking an existing merge commit always fails with git's own "commit is a merge but no -m option was given." The history/log parser already handles merge commits (multiple parents) correctly, so this reads as a missed step rather than a deliberate cut — revert/cherry-pick are listed "done" in the roadmap, unlike merge/rebase which are explicitly out of scope.

### 4. `invoke_git_process` decodes subprocess output with no pinned encoding — MEDIUM-HIGH — **[confirmed]** — **FIXED**

`subprocess.run(...)` now passes `encoding="utf-8"` explicitly (kept alongside `errors="replace"` as a fallback for genuinely malformed bytes); the bytes-decode fallback path in `_normalize_process_output` was also pinned to UTF-8.

`src/opencobol2/git/process.py:76-86`

`subprocess.run(..., capture_output=True, text=True, errors="replace", ...)` has no `encoding=` argument, so decoding falls back to `locale.getpreferredencoding()` — commonly a legacy Windows code page, not UTF-8, unless UTF-8 mode is forced. Git's porcelain output (read with `-z`, disabling path quoting) carries raw UTF-8 bytes for non-ASCII names/messages. Every other storage layer in this codebase (`project/storage.py`, `settings/storage.py`, `documents/storage.py`) explicitly pins `encoding="utf-8"`; this is the one outlier. Combined with `errors="replace"` (not `surrogateescape`), a mis-decoded non-ASCII path becomes irreversibly corrupted (`U+FFFD`) and can no longer round-trip back into `stage_paths`/`unstage_paths` — `git add -- <corrupted-path>` then fails with "pathspec did not match any files." No test exercises a non-ASCII path or commit message.

### 5. Single, non-overridable per-instance command timeout applies to network operations too — MEDIUM — **[confirmed]** — **FIXED**

`_invoke` now accepts an optional per-call `timeout_seconds` override (falling back to the service-wide default when omitted), and `clone_repository`/`fetch`/`pull`/`push` all expose it as a keyword parameter. Regression test: `test_fetch_timeout_override_passed_through`.

`src/opencobol2/services/git.py:200-289`, `2068-2091`

`timeout_seconds` (default 30s) is fixed at `GitService` construction and used identically for local `status`/`add` and for `clone`/`fetch`/`pull`/`push`. A legitimately slow clone/fetch over a slow link is killed at 30s and reported as a timeout, with no per-call override available.

### 6. Conflict/clone-failure classification is pure stdout/stderr substring matching — LOW — **[plausible, unconfirmed]** — **DEFERRED**

Left as-is: no concrete real-git message was found that both triggers a false match and is unrelated to the condition being tested for, and a structural rewrite (parsing exit codes / `MERGE_HEAD` presence instead of substrings) is a larger design change than warranted for a design-fragility finding with no live reproduction.

`src/opencobol2/services/git.py:2321-2424`

`_looks_like_clone_source_failure`/`_looks_like_merge_conflict` match marker words (`"conflict"`, `"could not apply"`, `"not found"`, `"unable to access"`) against lower-cased combined output rather than a structural signal (e.g. presence of `MERGE_HEAD`, git's own exit codes). No concrete real-git message was found that both triggers a false match and is unrelated to the condition being tested for, so this is a design fragility rather than a confirmed misclassification today.

### 7. No `GIT_TERMINAL_PROMPT=0` override for network operations — LOW — **[plausible, unconfirmed]** — **FIXED**

`invoke_git_process` now sets `GIT_TERMINAL_PROMPT=0` in the subprocess environment via `setdefault` (so an explicit caller override is still respected), for every invocation. Regression tests: `test_invoke_git_process_disables_terminal_prompt_by_default`, `test_invoke_git_process_respects_explicit_terminal_prompt_override`.

`src/opencobol2/services/git.py:2076-2091`

Nothing disables interactive credential prompting for `fetch`/`pull`/`push`/`clone_repository`. On Windows, Git Credential Manager can pop a native GUI dialog for an authentication-required remote instead of failing fast on stderr; if ignored, the operation is eventually just killed and reported as "timed out" rather than "authentication needed." Not tested against a real authenticated remote.

## Command / menu / toolbar contribution framework

Files: `src/opencobol2/commands/*.py`, `src/opencobol2/services/commands.py`, `src/opencobol2/services/command_contributions.py`

### 1. A `DynamicMenuProvider` exception (or a stale command-ID reference) aborts resolution of the *entire* menu surface — HIGH — **[confirmed, with a real production trigger]** — **FIXED**

`resolve_surface` now isolates each contribution's resolution in its own try/except — a raising direct contribution, a raising dynamic-menu provider, or a single bad item within an otherwise-good provider's output is skipped individually rather than aborting the whole surface. Regression tests: `test_service_skips_contribution_for_missing_command`, `test_service_skips_only_broken_contribution_among_others`, `test_dynamic_menu_provider_producing_invalid_items_is_isolated`.

`src/opencobol2/services/command_contributions.py:235-256` (`_resolve_dynamic_menu_contribution`)

`contribution.provider(context)` and the subsequent `self._command_service.get_command(item.command_id)` lookup are not wrapped in exception handling beyond a narrow `tuple(...)` `TypeError` catch. Any other exception propagates out of `resolve_surface()`, discarding every other already-resolved contribution on that surface.

**Concrete trigger:** the real recent-projects provider (`src/opencobol2/gui/project_commands.py:355-381`, `provide_recent_projects`) filters with `path.is_file()` for every path in `recent_projects.paths`, with no try/except. `Path.is_file()` does not catch `ValueError` (e.g. a path string containing an embedded null byte, reachable from a corrupted/hand-edited settings file). That `ValueError` propagates through `resolve_surface(MENU, "file")` and up through `command_menus.py:populate_menu`, which has *already called `menu.clear()`* — so the File menu ends up empty/broken via an unhandled exception surfacing through Qt's `aboutToShow` signal. No test exercises a raising provider.

### 2. No cycle/self-reference guard on submenu contributions, and the real consumer recurses with no visited-set — MEDIUM — **[confirmed mechanism, no live trigger in the current built-in catalog]** — **FIXED**

`connect_menu`/`populate_menu` now thread an `_ancestor_surface_ids` set down the recursion; a submenu whose `submenu_id` is already an ancestor is skipped rather than recursed into, breaking any cycle one level in (so e.g. a direct A→A self-reference still renders the "A" entry once, just with an empty nested submenu, rather than vanishing outright or recursing forever). Regression tests: `test_populate_menu_breaks_self_referencing_submenu_cycle`.

`src/opencobol2/commands/contributions.py:110-193` (`SubmenuContribution.__post_init__`), `src/opencobol2/gui/command_menus.py:103-123`

Nothing checks `submenu_id == surface_id`, and nothing detects a cycle across two submenus (A's `submenu_id` == B's `surface_id` and vice versa). The GUI's `connect_menu` → `populate_menu` → `connect_menu` recursion carries no visited-ID set. Not triggered by the current single-level built-in catalog, but unprotected against a future/plugin-contributed cyclic registration, which would hang/crash on `RecursionError` the moment the menu is shown.

### 3. Dynamic-menu-item `enabled` override is enforced from a stale snapshot, not re-derived at execution time — MEDIUM — **[confirmed]** — **FIXED**

`execute_dynamic_item` now re-derives the command's state fresh and recombines it with the item's own `enabled` override immediately before executing, instead of trusting the `ResolvedDynamicMenuItem` snapshot captured at the last `resolve_surface()` call — this matters because `CommandService.execute()`'s own fresh re-check has no notion of a per-item override at all, so it can't enforce that half by itself.

`src/opencobol2/services/command_contributions.py:189-213`

`execute_dynamic_item` checks `item.state.enabled` from the `ResolvedDynamicMenuItem` captured at the *last* `resolve_surface()` call — never re-evaluated before executing. By contrast, `CommandService.execute()` always calls `command.state(context)` fresh immediately before checking `enabled` (`services/commands.py:76-102`). If an item's per-item `enabled` override depends on live conditions that change between resolution and execution, a caller holding the old resolved object can execute an item that would now resolve as disabled.

### 4. Handler-mapping keys are never cross-validated against the actual built-in command-ID catalog — LOW/MEDIUM — **[confirmed]** — **FIXED (adjacent gap, same root cause)**

Rather than special-casing `BuiltInCommandHandlers`, added `CommandContributionService.validate_contributions()`, which cross-checks every *contribution*'s `command_id` against the live `CommandRegistry` and returns the offending contribution IDs. Wired into `gui/application.py`'s bootstrap right after the contribution service is built, raising a clear `RuntimeError` at startup if any exist — this is more load-bearing now than it would have been standalone, since fix #1 above makes a bad `command_id` reference silently invisible at runtime (isolated and skipped rather than crashing), so a static, fail-fast startup check is what actually catches the typo going forward. Regression tests: `test_validate_contributions_reports_missing_command`, `test_validate_contributions_returns_empty_when_all_resolve`.

`src/opencobol2/commands/builtins.py:222-292`

`BuiltInCommandHandlers` validates its keys are non-empty, pre-stripped strings mapping to callables, but never checks membership against `BuiltInCommandIds`. A typo'd key (e.g. `"file.svae"`) is silently accepted at construction; the real `FILE_SAVE` command keeps its `unconfigured_handler` and only fails at the moment it's actually invoked, with a `BuiltInCommandHandlerNotConfiguredError` message disconnected from the actual typo.

### 5. `separator_before`/`separator_after` live on the same contribution that visibility hides — LOW — **[confirmed interaction, no test coverage]** — **FIXED**

`gui/command_menus.py` and `gui/toolbars.py` now resolve with `include_hidden=True` and gate only the `addAction`/`addMenu` call on `state.visible` — the contribution's own separator flags render regardless, so a hidden item's neighbors keep their intended visual boundary instead of losing it along with the item. Regression test: `test_populate_menu_keeps_separator_around_hidden_contribution`.

`src/opencobol2/services/command_contributions.py` (`resolve_surface` visibility filtering)

If the contribution carrying `separator_before=True` becomes hidden via its own `state_provider`, the visual group boundary disappears along with it. Not necessarily a bug by design, but an untested interaction between two independent features.

### 6. Test filename typo (cosmetic) — **[verified]** — **FIXED**

Renamed via `git mv` to `tests/unit/test_command_contribution_service.py`, preserving history.

`tests/unit/test_commant_contribution_service.py` — "commant" should be "command." Does not affect pytest discovery (still matches `test_*.py`), purely a real typo in the file's actual name.

## Settings framework + persistence

### 1. No error handling around settings load at application startup — HIGH — **[verified]** — **FIXED**

## Cross-cutting observations (Phase 1)

- **Error-handling asymmetry across subsystems.** The codebase already has an established, good pattern for "a downstream failure shouldn't crash the whole bootstrap" (Git-repository discovery in `application.py` explicitly catches and degrades). That pattern was not applied consistently to: settings load at startup, dynamic menu provider resolution, or status bar item refresh — all three currently let one failure take down something much larger than the thing that actually failed. **Resolved** — all three now follow the same isolate-and-degrade pattern (Settings §1, Commands §1, Status Bar §1).
- **The `"--"` argument-separator convention in `GitService` is inconsistently applied** — present for every branch/tag/remote/sync command, absent for reset/history/revert/cherry-pick/diff. Worth a single sweep to apply it everywhere ref-like user input reaches a git command line, rather than fixing each call site ad hoc. **Resolved** — Git §2's fix applied the equivalent protection (leading-dash rejection at the shared validator, plus a trailing `--` at each call site) across all five previously-missing commands in one sweep, exactly as suggested here.
- **Encoding is the most under-tested dimension in this phase.** Both the Git process runner and the document storage layer make encoding assumptions with no non-ASCII test coverage anywhere in Phase 1, and both would reportedly fail (crash or corrupt) on legacy 8-bit COBOL source or non-ASCII paths/messages. **Resolved** — Git §4 pinned `encoding="utf-8"` on the process runner, and Documents §1 turned the document-storage decode failure into a caught, user-visible error instead of an uncaught crash; both now have regression tests exercising the previously-uncovered non-ASCII/wrong-encoding path.

False
>>> Path("E:payload/nc.exe").parts
('E:', 'payload', 'nc.exe')          # no ".." present either, so the traversal check also passes

This affects every field validated by this function: `VirtualFolder.member_paths`, `ProjectTask.working_directory`, `LaunchConfiguration.executable_path`/`working_directory`, and `ProjectProperties.output_directory`. ## 2. Invalid/truncated UTF-8 in a project file crashes ungracefully — HIGH — **[verified]** — **FIXED**

Added an `except UnicodeDecodeError` clause ahead of the existing `except json.JSONDecodeError`, converting it to the same documented `ProjectFormatError` ("Project file is not valid UTF-8.") instead of letting the raw stdlib exception escape. Regression test: `test_load_rejects_invalid_utf8`.

`src/opencobol2/project/storage.py:73-82` (`ProjectStorage.load`)

```python

except json.JSONDecodeError as error:
    raise ProjectFormatError(...) from error
```
`read_text(encoding="utf-8")` is inside the `try`, but a decode failure raises `UnicodeDecodeError`, which is not a subclass of `json.JSONDecodeError` — confirmed directly by reading the exception hierarchy and the exact except clause. A project file with a single invalid UTF-8 byte (truncated mid multi-byte character, wrong-encoding save from another tool, disk corruption) propagates a raw `UnicodeDecodeError` instead of the documented `ProjectFormatError`, contrary to the "clear error for malformed project files" behavior every other decode error in this same function correctly provides.

## 3. A project can be saved in a schema version its own loader rejects — MEDIUM — **[confirmed]** — **FIXED**

`Project.__post_init__` now requires `schema_version == CURRENT_PROJECT_SCHEMA_VERSION` exactly, rather than merely positive. Regression test: `test_project_rejects_non_current_schema_version` (the pre-existing `test_project_rejects_invalid_schema_version` for `schema_version=0` was updated to match the new, more general error message).

`src/opencobol2/project/storage.py:88-126` (`save`), cross-referenced against `Project.__post_init__`

## 4. Deeply nested virtual folders crash the loader with a bare `RecursionError` — MEDIUM/LOW — **[reported as directly reproduced with a ~2000-level-deep nested structure]** — **FIXED**

## 5. Environment-variable override keys are case-sensitive, on a platform where env vars are not — MEDIUM — **[confirmed at the model layer; the merge-layer consequence was empirically tested and found not to break precedence today, but relies on incidental behavior]** — **FIXED (both layers)**

Model layer: `_require_string_mapping` now rejects case-insensitively-colliding keys within one `environment_overrides` map (e.g. `{'PATH': 'a', 'Path': 'b'}`), closing the "obviously ambiguous within a single map" half. Merge layer (`_merge_environment` in `services/project.py`): now does a case-insensitive-aware merge *when `os.name == "nt"`* — when applying an override key, it looks up any existing key that matches case-insensitively and replaces it (rather than `dict.update()` treating the differently-cased key as a brand new entry), so an ambient `Path` and an override `PATH` collapse into one deterministic entry instead of both riding along into `subprocess.run(env=...)`. Deliberately gated on `os.name == "nt"`: on POSIX, `PATH` and `Path` are genuinely two different variables, and case-folding them there would be the actual regression, not a fix — confirmed by testing both platform branches. Regression tests: `test_project_task_rejects_case_insensitively_colliding_env_keys`, `test_run_task_environment_merge_is_case_insensitive_on_windows`, `test_run_task_environment_merge_stays_case_sensitive_off_windows`.

`src/opencobol2/project/models.py:984-1019` (`_require_string_mapping`) validates only type, never case-insensitive key uniqueness — confirmed that `ProjectTask(..., environment_overrides={'PATH': 'a', 'Path': 'b'})` is accepted, both within one override map and across the project/task/launch-config layers. The actual merge (`_merge_environment` in `src/opencobol2/services/project.py:140-156`) starts from `dict(os.environ)` and applies plain `dict.update()` calls per layer — since a plain `dict` is case-sensitive but Windows environment variables are not, a project-level `PATH` and a task-level `Path` become two distinct dict keys handed to `subprocess.run(env=...)` rather than one cleanly overriding the other. The second review pass empirically ran this through a real `subprocess.run`/`CreateProcess` call and found the later-inserted key happened to win — so precedence isn't demonstrably broken today — but the result relies on incidental dict-insertion-order behavior rather than an explicit case-fold merge, and an easy real-world typo (setting `PATH` at one layer, `Path` at another) produces an ambiguous, unvalidated result either way.

## 8. Process timeout only kills the direct child, not any grandchildren it spawns — MEDIUM — **[plausible, unconfirmed]** — **DEFERRED**

`src/opencobol2/project/process.py:86-118`

Not demonstrated live (would require a real multi-process COBOL build chain to construct), but a well-documented general limitation of this exact subprocess/timeout pattern with no mitigation here.

## 1. Bookmark/breakpoint lost forever if its line is deleted and the delete is undone — HIGH — **[verified]** — **DEFERRED (assessed in depth)**

Not fixed, after real investigation rather than a quick pass: the obvious approach — intercept `undo()`/`redo()` on `SourceEditorWidget` and re-associate a just-pruned bookmark/breakpoint with whatever block reappears at the same position — doesn't actually work here, because pruning isn't lazy-on-undo, it's aggressive and constant. `_prune_invalid_bookmarks`/`_prune_invalid_breakpoints` run inside the `bookmarked_lines`/`breakpoint_lines` property getters, which the gutter calls on *every repaint* (`paint_line_number_area` reads `bookmarked_lines` each time, `editor.py:759-760`). By the time a user could ever press Ctrl+Z after a delete, at least one repaint has almost certainly already happened, and the invalidated `QTextBlock` — along with any information about which line it used to be — is already gone. A real fix would need to capture a durable fingerprint (line number + text) of a bookmark/breakpoint *before* it goes invalid, likely via `QTextDocument.contentsChange`, and match it back up against newly-inserted content on undo without producing false-positive resurrections (e.g. two unrelated blank-line edits shouldn't accidentally swap bookmarks). That's a real design change to how this state is tracked, not a scoped patch, and I have no interactive Qt session available to verify the many edit/undo/redo edge cases such a change would need to get right — shipping it undertested felt worse than leaving this documented. This also matches this codebase's own cross-cutting observation on this exact finding (below): it was already flagged as a shared-pattern concern worth a dedicated pass, not a one-line fix.

`src/opencobol2/gui/editor.py:1251-1305` (`toggle_bookmark_at_cursor`/`_prune_invalid_bookmarks`), `:1307-1363` (the breakpoint mirror)

Bookmarks/breakpoints are tracked via live `QTextBlock` handles specifically so they survive edits *elsewhere* in the document — this is a deliberate, previously-established pattern in this codebase for exactly this staleness problem. But when the underlying block is actually deleted (not just shifted), `block.isValid()` becomes `False` and the entry is pruned. Pressing Undo afterward restores the visible text exactly, but Qt's undo re-inserts new document content rather than reviving the original `QTextBlock` object — so the marker never reappears even though the text is back to identical. Reported as directly reproduced: bookmark line 2 of a 3-line document, delete that entire line, undo — text is restored byte-for-byte but `editor.bookmarked_lines == ()`; identical result for breakpoints. Concrete trigger: bookmark/breakpoint a line, delete the whole line (select + Delete, or Backspace across it), then Ctrl+Z. The marker is gone with no further action and no UI indication it was lost.

## 2. Printing ignores code folding entirely — HIGH — **[reported as empirically verified via real PDF generation: a document with 500 lines folded away printed a PDF byte-for-byte identical in size (467,150 bytes) to the same 500 lines fully visible, versus 3,395 bytes for a genuinely 3-line document]** — **FIXED (warn, don't silently reimplement printing)**

Deliberately not implemented as "only print what's visible": that would mean reimplementing printing against a filtered document, and a printout *silently missing source lines* because they happened to be folded on screen is arguably a worse surprise than the current one — most developers printing source code want everything, regardless of transient fold state. Instead, `print_active_tab` now checks `editor._collapsed_start_lines` and, if any fold is active, shows `QMessageBox.question` ("this document has folded sections; printing always includes their full content — continue?") before proceeding; declining aborts the print (returns `False`, matching the method's existing "did printing happen" contract). Regression tests: `test_print_active_tab_warns_before_printing_folded_content`, `test_print_active_tab_proceeds_when_fold_warning_is_confirmed`, `test_print_active_tab_does_not_warn_without_any_folds`.

`src/opencobol2/gui/editor.py:2606-2623` (`EditorTabsWidget.print_active_tab`, delegating straight to `QPlainTextEdit.print_()`) vs. `:1943-1976` (`_hide_range`/`_show_range`, which hide folded content only via `QTextBlock.setVisible(False)`)

`QPlainTextEdit.print_()` uses the standard document print/layout path, which doesn't consult per-block visibility — that flag only affects the editing widget's own on-screen viewport layout, not printing. Concrete trigger: collapse a large section to keep the visible file short on screen, then File > Print — the printed output silently includes every folded-away line, potentially producing far more pages than what's visible on screen suggests, with nothing telling the user this happened.

## 3. Fold ranges go stale on any edit that doesn't change the line count — MEDIUM — **[reported as directly reproduced]** — **FIXED**

The fold-range recompute connection was switched from `blockCountChanged` to `textChanged`, so any edit — not just ones that add or remove a line — triggers a recompute, including the in-place same-line-count case this finding describes. Regression test: `test_in_place_edit_with_no_line_count_change_refreshes_fold_ranges` (`tests/unit/test_gui_editor_folding.py`), which reproduces the exact `IF`→`DISPLAY` in-place rewrite from the original report and asserts the stale `(5, 7)`-style range is gone and the correct new range (or none) is in its place.

`src/opencobol2/gui/editor.py:504-506` (fold-range recompute wired only to `blockCountChanged`), `:2011-2035` (`_update_fold_ranges`), consumed by `toggle_fold` (`:1876-1898`)

Fold ranges only recompute when the document's block (line) count changes. An in-place edit that keeps the same number of lines — e.g. overwriting `IF 1 > 0` with `DISPLAY 1` on the same physical line — leaves the old fold range untouched. Reported as directly reproduced: replacing an `IF` line's text in-place with a `DISPLAY` statement (same line count) leaves the stale `(5, 7)` fold range intact; calling `toggle_fold(5)` afterward still collapses the lines that used to be that `IF`'s body, even though line 5 is no longer an `IF` at all. Concrete trigger: with folding enabled, edit the text of a fold-start or fold-body line without adding/removing a newline, then click the now-stale gutter fold marker.

## 4. Tab characters corrupt syntax-highlight and diagnostic-underline positions — HIGH — **[verified]** — **FIXED (at the input boundary, not the lexer/highlighter mismatch itself)**

Fixed by preventing the Tab key from inserting a literal `\t` in the first place rather than reconciling the lexer's tab-expanded columns with the highlighter's raw-text columns after the fact: `SourceEditorWidget.keyPressEvent` now intercepts `Qt.Key.Key_Tab` and, when `EditorSettings.insert_spaces` is enabled (the default — `insert_spaces: bool = True` in `settings/models.py:156`), inserts enough spaces to round up to the next tab stop instead of a real tab character. This closes the practical exposure for anyone indenting through this editor with default settings, but does **not** fix the underlying column-math mismatch between the lexer (`raw_line.expandtabs(...)`) and the highlighter (raw, un-expanded document text) — a file already containing literal tabs (opened from disk, pasted, or authored with `insert_spaces` disabled) still corrupts highlight/diagnostic positions exactly as originally reported. Regression tests: `test_tab_key_inserts_spaces_when_insert_spaces_enabled`, `test_tab_key_rounds_up_to_next_tab_stop`, `test_tab_key_inserts_literal_tab_when_insert_spaces_disabled` (the last one pins down, deliberately, that the gap still exists when the setting is off).

`src/opencobol2/gui/syntax_highlighter.py:141-173` (`highlightBlock`), root cause traced to `src/opencobol2/language/lexer.py:315` (`raw_line.expandtabs(...)`)

The lexer computes every token's/diagnostic's `column` against a tab-*expanded* copy of each line, but the highlighter feeds `self.document().toPlainText()` — the raw, un-expanded Qt document text — into the lexer, then applies the resulting (tab-expanded) column offsets directly against that same raw text via `setFormat(token.span.start.column - 1, len(token.text), format_)`. Confirmed by reading both sides of this mismatch directly: whenever a line contains a tab character before a token, every subsequent token's highlight lands shifted from where the real text actually is. The reviewing pass additionally confirmed this concretely: for source `"\tMOVE A TO B."`, the lexer reports `MOVE` at column 9 (post-tab-expansion), but rendered through the real highlighter this colors the substrings `"TO"` and `" B"` in keyword-blue while `MOVE` itself gets no highlight at all. `SourceEditorWidget` doesn't override tab handling, so pressing Tab inserts a literal `\t` — trivially reachable by any user who indents with Tab rather than spaces.

## 5. An edit on one line can leave a different, untouched line's highlighting stale — HIGH — **[reported as directly reproduced via a scripted repro comparing the highlighter's own retokenized ground truth against its actually-rendered formatting]** — **FIXED**

Fixed by giving the highlighter a deferred full-document rehighlight: `highlightBlock` now calls `self._schedule_full_rehighlight()` after every retokenize, which starts a `QTimer(self)` (parented to the highlighter, single-shot, 0ms interval) connected to `self.rehighlight`. The 0ms/queued timer is necessary rather than calling `rehighlight()` directly, since `rehighlight()` from inside `highlightBlock` itself would recurse; deferring it to the next event-loop tick lets Qt finish the current block first, then re-run every block (correctly re-coloring untouched lines whose *meaning* changed even though their own text didn't). One self-inflicted bug surfaced and was fixed during this work, not shipped: the first version used the static `QTimer.singleShot(0, self.rehighlight)`, which crashed with `RuntimeError: ... libshiboken: Internal C++ object (CobolSyntaxHighlighter) already deleted` when a *different* test's highlighter had already been garbage-collected by the time its queued callback fired — parenting the timer to the highlighter itself means Qt cancels the pending callback as part of the normal parent-child teardown, so a destroyed highlighter can never receive a callback for a document that no longer exists. Regression test: `test_editing_one_line_refreshes_a_different_untouched_line` (`tests/unit/test_gui_syntax_highlighter.py`) — reproduces the exact continuation-literal-termination scenario from the original report and calls `qapp.processEvents()` to let the deferred timer actually fire before asserting line 1 picked up its new coloring.

`src/opencobol2/gui/syntax_highlighter.py:141-173` (`highlightBlock`/`_retokenize`)

The highlighter never uses Qt's `setCurrentBlockState`/`previousBlockState` cascade and never calls `self.rehighlight()` after re-tokenizing, relying entirely on Qt's own per-block dirty tracking — which only re-invokes `highlightBlock` for the block whose own text actually changed. For genuinely cross-line constructs (a COBOL continuation string literal spanning two lines), editing line *N* can change what tokens line *N+1* should have — but if line *N+1*'s own text wasn't touched, Qt never calls `highlightBlock` for it, so it keeps its old (now-wrong) formatting. Reported as directly reproduced: a continuation literal spanning lines 0–1 (both correctly left uncolored per the documented cross-line skip), then appending a single `'` to line 0 only. The highlighter's own retokenized ground truth now shows line 1 has become a complete, single-line string literal that should be colored — but the actually-rendered format on that block remains empty, because Qt never re-invoked `highlightBlock` for it. The string literal stays invisible until the user separately edits that exact line.

## 6. Minimap's "visible viewport" indicator is badly wrong once folds hide content spanning the on-screen view — MEDIUM — **[reported as directly reproduced: correct indicator height should be ~398px (nearly the full minimap), computed value was ~21px — roughly 20x too small]** — **FIXED**

## Cross-cutting observations (Phase 3)

- **The "track state via a live `QTextBlock` handle instead of a plain line number" pattern — this codebase's own established fix for a prior staleness bug — has a real gap of its own**: it survives a block being *shifted*, but not a block being *deleted-then-undone*, since Qt's undo re-inserts new blocks rather than reviving the old object reference. Worth revisiting as a shared concern, since bookmarks and breakpoints both inherit it identically, and any future Phase 3 feature built on the same pattern would too. **Unresolved** — this is exactly finding §1, which was assessed in depth and deliberately deferred rather than shipped half-verified; see its tag for the full reasoning. Nothing else in this phase touches this pattern, so the gap stands as originally described.
- **Two independent, unrelated features (printing, coding-area guides) both silently assume "one visual row == one logical line starting at column 1,"** and both break for the same underlying reason: this editor doesn't force `NoWrap`, and folding/printing/guide-painting code was written as if wrapping and folding-driven visibility never interact with layout. A single design decision (either force `NoWrap`, or make all of these features properly folding/wrap-aware) would resolve several independent findings at once. **Resolved, via the first option**: `SourceEditorWidget` now calls `setLineWrapMode(NoWrap)` unconditionally (§8's fix), so the assumption these features were built on now actually holds; the minimap's viewport-sizing fix (§6) explicitly depends on this same change (see its `_last_visible_block_number` docstring). Printing (§2) took a different, narrower path — a warning rather than a folding-aware reimplementation — since it isn't affected by word-wrap in the first place (Qt's print path lays out the full document independent of the on-screen viewport).
- **The syntax highlighter's fundamental structural gap — no cross-block state cascade (`setCurrentBlockState`/`previousBlockState`) and no `rehighlight()` after re-tokenizing** — is the root cause of both the tab-corruption finding and the stale-cross-line-highlighting finding. These read as two symptoms of one missing piece of Qt `QSyntaxHighlighter` plumbing, not two unrelated bugs. **Partially resolved**: the missing `rehighlight()` half is now fixed (§5, via a parented deferred `QTimer`), which directly closes the stale-cross-line-highlighting finding. The tab-corruption finding (§4) was fixed differently and more narrowly — by stopping literal tabs from reaching the document via typing, not by reconciling the lexer's tab-expanded columns with the highlighter's raw-text columns — so the underlying column-math mismatch these two findings share a root cause with is still live for any tab character that reaches a document some other way (opened from disk, pasted, or typed with `insert_spaces` disabled). A real fix for that residual gap would mean making the highlighter tab-expansion-aware (or stripping/normalizing tabs on load), which wasn't attempted here.

## Lexer (`lexer.py`, `tokens.py`)

Re-audit note: Lexer-1 through Lexer-7 were independently re-derived and re-executed against `tests/unit/test_cobol_lexer.py` (the actual test file for this subsystem) and the current lexer; all seven reproduce exactly as originally described, with no code drift since the original pass. One test-coverage note surfaced in the process: `test_debug_indicator_line_lexes_as_code` in that file actively **asserts Lexer-5's buggy D-indicator behavior as the expected outcome** — it locks the bug in rather than guarding against it, and will need inverting if Lexer-5 is ever fixed.

### Lexer-1. Free-format leading-`*` swallows a valid statement continuation as a full-line comment — HIGH — **[verified]** — **FIXED**

Fixed by requiring the real `*>` marker for a free-format whole-line comment (`expanded_line.lstrip().startswith("*>")`), matching the only comment marker free-format COBOL actually defines — a bare `*` alone is the multiplication operator, not a comment indicator, in free format (fixed format's own `*`-in-column-7 convention is unaffected; this change is scoped to the free-format branch of `_prepare_lines` only). The prior test that asserted a bare `* text` line was a comment was itself encoding this bug; it's been corrected to use `*>` and a new test proves the actual repro (a COMPUTE statement continued via a bare `*` onto its own line) is no longer swallowed. Regression tests: `test_free_format_line_starting_with_comment_marker_is_comment`, `test_free_format_bare_asterisk_continuation_is_not_swallowed_as_comment` (`tests/unit/test_cobol_lexer.py`).

`src/opencobol2/language/lexer.py:346-350` (free-format branch of `_prepare_lines`): `is_comment = expanded_line.lstrip().startswith("*")` fires for any line whose first non-blank character is `*`, not just the `*>` inline-comment marker free format actually uses. Free-format COBOL lets one statement flow across physical lines with no continuation marker, so a multiplication expression continued onto its own line is misread as a comment.

Directly reproduced:
```cobol
COMPUTE TOTAL = QUANTITY
    * PRICE.
```
tokenizes to `COMPUTE`, `TOTAL`, `=`, `QUANTITY`, then a single `COMMENT` token for `'    * PRICE.'` — the multiply operator, `PRICE`, and the terminating period vanish entirely, with zero diagnostics raised.

### Lexer-2. Tab expansion used for column math doesn't match the raw character offsets several consumers assume — HIGH — **[verified the lexer/highlighter half directly under Phase 3; the quick-fix half is independently reconfirmed below under Editor-Facing-2]** — **DEFERRED**

Not fixed at the lexer level. A real fix here means giving every token a second, raw (non-tab-expanded) column alongside its existing tab-expanded one, and auditing every consumer (syntax highlighter, Quick Fix, `go_to_line`, and any future one) to use whichever is actually correct for its own indexing target — a cross-cutting API change to `Token`/`SourceSpan`, not a scoped lexer patch, and one that would need to thread through the parser/semantic layers too since spans propagate from lexer tokens into AST nodes and diagnostics. The practical exposure is already substantially reduced: Phase 3's fix for the syntax-highlighter half of this exact bug converts typed tabs to spaces at the input boundary whenever `insert_spaces` is enabled (the default), so the common "user presses Tab while editing" path no longer produces literal tabs at all. What remains is files that already contain literal tabs from another source (opened from disk, pasted, or `insert_spaces` disabled) — a real, documented residual gap (see the Phase 3 tracker's own cross-cutting notes), not one this pass attempted to close given the scope of an actual fix. Editor-Facing-2 (Quick Fix's own instance of this same mismatch) is deferred alongside it for the identical reason.

### Lexer-3. A comment line interrupting a continued string literal is treated as fatal termination rather than transparently skipped — MEDIUM — **[confirmed by reading the exact branch condition; COBOL-standard conformance of the trigger itself is unconfirmed]** — **FIXED**

Fixed by making a comment line never terminate a pending literal: `tokenize()`'s comment-line branch used to unconditionally finalize any pending literal before emitting the comment token; it now always transparently skips past (the comment token is still emitted, so the interrupting comment stays visible/colorable — only the literal-termination side effect was removed). The pending literal correctly resumes on the next `-` continuation line exactly as before the interruption. Regression test: `test_comment_line_interrupting_a_continued_literal_is_transparent` (`tests/unit/test_cobol_lexer.py`), using the exact repro from this finding and asserting zero diagnostics, the fully-glued literal value, and that the comment token itself still comes through.

`lexer.py:173-196`: whenever a literal is still pending and the current line is classified as a comment, the lexer unconditionally emits an "not terminated" ERROR and abandons the literal, even when the very next physical line is a valid `-` continuation of it.

```cobol
       01  X VALUE 'THIS IS A VERY LONG MESS
      * a note
      -    'AGE THAT CONTINUES'.
```
produces an ERROR, an unrelated WARNING ("Continuation line found without a literal to continue"), and a spurious extra literal token parsed as fresh code on the continuation line — none of which reflects the source's evident intent.

### Lexer-4. Unterminated/comment-interrupted literal tokens always get a zero-length span regardless of their actual text length — MEDIUM — **[confirmed]** — **FIXED**

Fixed by giving `_PendingLiteral` a `last_position` field, updated every time content is consumed into it (both at initial creation when a literal isn't closed by end of line, and at the end of `_scan_line` when a continuation line is fully swallowed with still no closing quote), and using it as the finalized token's span end instead of reusing `start_position` for both ends. Regression test: `test_unterminated_literal_span_reflects_its_actual_text_length` (`tests/unit/test_cobol_lexer.py`), asserting the span's start and end now differ and that the column delta equals the literal's actual text length.

`lexer.py:409-429` (`_finalize_pending_literal`): `span=SourceSpan(start=pending_literal.start_position, end=pending_literal.start_position)` — start and end are identical no matter how long the literal's text is. Any consumer that highlights or selects by span (the diagnostic underline, a hypothetical better Quick Fix) gets a range covering nothing rather than the literal's actual extent.

### Lexer-5. `D`/`d`-indicator (WITH DEBUGGING MODE) lines are unconditionally lexed as live code, and the indicator is discarded before reaching any `Token` — MEDIUM — **[confirmed]** — **DEFERRED**

Not fixed. The lexer processes lines one at a time with no visibility into whether `WITH DEBUGGING MODE` was declared elsewhere in the same compilation unit's `SOURCE-COMPUTER` paragraph — correctly implementing this would mean either a two-pass lexer (scan for the directive first, then re-lex with that context) or threading a mutable "debugging mode enabled" flag through what is currently a straightforward single-pass, stateless-per-line design. That's a real feature addition, not a scoped bug fix, and guessing a default (e.g. "always treat D-lines as comments since debugging mode is rarely enabled") would silently change behavior for the (presumably rare but real) case where it genuinely is enabled — trading one silent misinterpretation for another rather than fixing the root problem. Left as documented, unfixed, consistent with this tracker's convention of deferring genuine design-level gaps rather than shipping a guess.

`lexer.py:34-42`: a `D` in the indicator column is treated exactly like a blank indicator, and `_PreparedLine.indicator` never survives into a `Token`. Per the COBOL standard, a D-line only compiles when `WITH DEBUGGING MODE` is declared; otherwise a real compiler excludes it like a comment. Since no later stage can recover the indicator, a debug-only line referencing a variable that doesn't otherwise exist produces a false "undefined identifier" diagnostic on source a real compiler would never even see.

### Lexer-6. Decimal numeric-literal values are parsed with `float()`, losing precision for realistic COBOL fixed-point magnitudes — MEDIUM — **[verified]** — **FIXED**

Fixed by switching to `decimal.Decimal` for every fractional/exponent-bearing numeral's `.value` (plain integers keep `int`, which already has arbitrary precision and was never the problem). `Token.value`'s type annotation and runtime validation (`tokens.py`) were widened to accept `Decimal` alongside the existing `str`/`int`/`float`/`None`. Regression test: `test_decimal_numeric_literal_does_not_lose_precision` (`tests/unit/test_cobol_lexer.py`), using this finding's own `123456789012345678.99` repro and asserting the parsed value round-trips exactly via `Decimal`.

`lexer.py:876-880`: `value=float(full_text)`. Confirmed: `float("123456789012345678.99")` loses both the fractional part and low-order integer digits (`Decimal(f) == 123456789012345680`) — the token's parsed `.value` diverges from what's actually written for any currency/fixed-point literal at realistic COBOL magnitudes (e.g. `PIC 9(15)V99`). `decimal.Decimal` would avoid this; nothing currently appears to consume `token.value` for this purpose, but it's a latent trap for any future feature that does (e.g. a hover showing a literal's parsed value).

### Lexer-7. `END_OF_FILE` token position can precede real tokens on the same line when the source has no trailing newline — LOW/MEDIUM — **[verified]** — **FIXED**

Fixed together with Lexer-9 below, since both share the identical root cause and identical fix: `tokenize()` now computes the EOF line as `len(prepared_lines) + 1` — always one line past the last physically-prepared line, the same line-accounting `_prepare_lines` (and therefore every real token) already uses — instead of `self._source.count("\n") + 1`. This generalizes the existing "EOF lands one line past the last real content line when the source ends with a trailing newline" behavior (already confirmed correct in the Phase 4 "Checked and found correct" note) to the no-trailing-newline case too, so EOF is never before a real token regardless of whether the file ends with a newline. Regression test: `test_end_of_file_position_is_never_before_a_real_token_without_trailing_newline` (`tests/unit/test_cobol_lexer.py`), using this finding's own no-trailing-newline repro.

`lexer.py:256-261` computes the EOF line via `self._source.count("\n") + 1`, while every real token's line comes from `str.splitlines()` — these disagree whenever the source has no trailing newline (or uses a line separator `splitlines()` recognizes but bare `\n`-counting doesn't). Confirmed: for `"...DISPLAY 'HI'.\n       STOP RUN."` (no final newline), real tokens on the last line sit at columns 8/13/16, but `END_OF_FILE` is placed at column 1 — before them, breaking the general expectation that EOF is the stream's last/highest position.

### Lexer-8. Signed numeric literals (`+123`, `-45.6`) are never merged into one token, and the behavior is completely untested — LOW — **[re-verified: verified]** — **DEFERRED**

Not fixed, deliberately. Merging a leading `+`/`-` into a numeral would require knowing whether that sign is genuinely a literal's sign or an arithmetic operator (`COMPUTE X = A - 5.` must keep `-` as subtraction, not fold it into a signed `-5`) — that's inherently a parser-level, token-context decision (is the preceding token something a value can be subtracted from, like an identifier/number/closing-paren, or not), not something the lexer can determine correctly on its own without look-behind logic that doesn't belong in a stateless single-pass tokenizer. This confirms rather than merely repeats the original finding's own suspicion ("plausibly intentional... reasonably left to the parser"): re-audit traced every call site and found neither `parser.py` nor `semantic.py` references `TokenKind.PLUS`/`TokenKind.MINUS` in a way that depends on sign-merging, so nothing downstream is broken by leaving this as-is.

`_ONE_CHARACTER_OPERATORS` always splits a leading `+`/`-` into its own token before digits are scanned. Plausibly intentional (sign vs. subtraction is genuinely context-dependent and reasonably left to the parser), but zero test coverage exists either way, so it's unverified as "intended" vs. "missed." Re-audit additionally confirmed neither `parser.py` nor `semantic.py` contains any reference to `TokenKind.PLUS`/`TokenKind.MINUS` at all — so this isn't compensated for anywhere downstream; the gap runs the full length of the pipeline.

### Lexer-9. `END_OF_FILE` token position can land *before* real, multi-line content when the source uses any line separator other than `\n` — MEDIUM — **[verified]** — **FIXED (same fix as Lexer-7)**

See Lexer-7 above — the `len(prepared_lines) + 1` fix resolves both findings at once, since neither depends on counting raw newline characters anymore. Regression test: `test_end_of_file_position_is_never_before_a_real_token_with_exotic_line_separators` (`tests/unit/test_cobol_lexer.py`), parametrized over all the separators this finding's report named (`\r`, vertical tab, form feed, file separator, and Unicode line/paragraph separators).

A broader, more severe variant of Lexer-7. `lexer.py:256-261` computes `last_line` via `self._source.count("\n") + 1`, but `str.splitlines()` (which drives every real token's line number through `_prepare_lines`) recognizes far more separators than bare `\n` — `\r`, `\v`, `\f`, `\x1c`, `\x1d`, `\x1e`, `\x85` (NEL), `
`, `
` — none of which contain a `\n` character. Lexer-7 only produces a wrong *column* on the correct line; this produces a wrong *line*, with EOF landing strictly before content spanning multiple physical lines.

Directly reproduced for six separators, e.g. old-Mac-style bare CR: `"       DISPLAY 'A'.\r       DISPLAY 'B'.\r"` — `splitlines()` correctly sees 2 lines and places `DISPLAY 'B'.` on line 2, but `count("\n")` is 0, so `END_OF_FILE` lands at `(1:1)` — a full line *behind* the second statement. Confirmed identically for vertical tab, form feed, file separator, and both Unicode line/paragraph separators. Legacy mainframe source that has passed through EBCDIC/ASCII conversion tooling is a plausible real-world vector for a stray control character — exactly the kind of source this IDE exists to import — and any consumer assuming EOF is the stream's last/highest position would get it wrong for the entire file, not just its last line.

### Lexer-10. Leading-decimal-point numeric literals (`.5`, `-.25`) aren't tokenized as numbers — the leading `.` is stolen as a bogus statement-terminating `PERIOD` token — HIGH — **[verified]** — **FIXED**

Fixed by adding a check in `_scan_line`'s main loop, before the one-character-operator fallback: when the current character is `.` and immediately followed by a digit, scan a numeral (`_scan_leading_dot_numeral`) instead of emitting a bare `PERIOD` token. The signed case (`-.25`) is handled the same way the lexer already handles every other signed numeral (Lexer-8, left deliberately split) — the `-` still tokenizes separately as `MINUS`, and `.25` is then picked up as its own numeral by this fix, consistent rather than a special case. Regression tests: `test_leading_decimal_point_numeric_literal`, `test_signed_leading_decimal_point_numeric_literal` (`tests/unit/test_cobol_lexer.py`).

Standard COBOL numeric-literal syntax allows a literal with no integer part (`[+|-] . digit...`). `.` is claimed by `_ONE_CHARACTER_OPERATORS` (`lexer.py:52-66`, mapped to `TokenKind.PERIOD`) before scanning ever reaches `_scan_word`, since `_scan_word` only fires when `character.isalnum()` (`lexer.py:604`) and `.` never satisfies that.

Directly reproduced: `COMPUTE X = .5 + Y.` tokenizes to `COMPUTE`, `X`, `=`, **`PERIOD`**, `NUMERIC_LITERAL(5)`, `PLUS`, `Y`, `PERIOD` — zero diagnostics. Since `PERIOD` is COBOL's own sentence/statement terminator, this doesn't just corrupt the literal's value (`0.5` becomes a stray token plus an unrelated bare `5`) — it injects a spurious statement terminator *in the middle of a live statement*, so any parser built on this token stream would believe `COMPUTE X = ` ends right there, with `5 + Y.` left dangling as the start of a phantom new sentence. Also reproduced combined with Lexer-8's sign-splitting: `COMPUTE X = -.5 + Y.` produces the identical corruption. Same silent, zero-diagnostic, cascading-impact class this tracker already treats as HIGH elsewhere (Lexer-1, Parser-1/2/4).

### Lexer-11. Scientific/E-notation numeric literals (`1.5E10`, `3.14E-2`) aren't recognized — the exponent silently becomes part of an unrelated identifier token — MEDIUM — **[verified]** — **FIXED**

Fixed by extending the numeral scan to consume an optional exponent suffix (`E`/`e`, optional sign, digits) after the integer/fraction part, via a shared `_scan_numeral_fraction_and_exponent` helper used both for ordinary digit-led numerals and the new leading-dot case (Lexer-10). One subtlety surfaced during implementation and required a second, targeted fix: a fraction-less numeral with an exponent (`5E3`, `5E-3`) is already fully consumed by the *existing* alnum/hyphen identifier-scanning loop before the code ever checks whether the word is purely digits — the `E` is alnum, and the hyphen-continuation rule meant for identifiers like `WS-COUNT` also happily continues through a signed exponent's `-`. A new `_looks_like_integer_with_exponent` check catches exactly this shape (`digits`, `E`, optional sign, `digits`, no fraction) as a sibling case to the ordinary all-digits branch. Regression tests: `test_scientific_notation_numeric_literal`, `test_scientific_notation_with_signed_exponent`, `test_integer_with_exponent_and_no_fraction` (`tests/unit/test_cobol_lexer.py`) — the last one specifically pins down the fraction-less case the naive fix initially missed.

COBOL (2002+, commonly used for `FLOAT-LONG`/`FLOAT-SHORT` literal constants) supports exponent notation. `_scan_word`'s fraction-handling branch (`lexer.py:843-883`) stops the moment digits run out after the decimal point and never checks for a trailing `E`/`e` exponent marker.

Directly reproduced: `COMPUTE X = 1.5E10.` tokenizes to `NUMERIC_LITERAL(text='1.5', value=1.5)`, then a wholly separate `IDENTIFIER(text='E10')`, then `PERIOD` — zero diagnostics, and the literal's magnitude is silently off by 10 orders of magnitude if anything ever trusts `.value`. Worse with an explicit exponent sign — `COMPUTE X = 3.14E-2.` — the hyphen-in-identifier rule (`lexer.py:817-823`) actively swallows it into one bogus identifier: `NUMERIC_LITERAL(3.14)`, `IDENTIFIER('E-2')`, `PERIOD`. No test exercises any exponent form.

## Parser / AST (`parser.py`, `ast_nodes.py`)

Re-audit note: all 8 findings below were independently re-derived and re-executed against the current `parser.py`/`ast_nodes.py` and `tests/unit/test_cobol_parser.py` (45 tests, all currently passing, none covering any of these 8 or the 4 new ones added below). All 8 reproduce exactly as originally described; Parser-2 and Parser-8 are upgraded from "reported"/"confirmed by inspection" to **[verified]** below since this pass executed them directly. Parser-4's downstream consequence was also found to be worse than originally written: diagnostics already collected *before* the crash point in the same parse are discarded too, not just hypothetical diagnostics after it — `parse_result.diagnostics` is only merged into `compute_source_diagnostics`'s running list after `parse_cobol_tokens()` returns successfully, so an uncaught crash loses everything from that call, not just "the rest of the file" in the narrower sense.

### Parser-1. `EXIT PERFORM` is silently destroyed into an orphaned `GenericStatement` plus a phantom, empty `PerformStatement` — HIGH — **[verified]** — **FIXED (together with Parser-9)**

Fixed by giving `EXIT` its own dedicated parse path (`_parse_exit`) instead of falling through to `_parse_generic_statement`, whose next-verb boundary check is exactly what mistook `PERFORM` for the start of a new statement. `_parse_exit` consumes `EXIT` plus an optional trailing `PERFORM`/`PARAGRAPH`/`SECTION`/`PROGRAM` operand as one unit, producing a single, intact `GenericStatement(verb='EXIT', tokens=('EXIT', 'PERFORM'))` with no phantom node. Regression test: `test_exit_perform_is_not_destroyed` (`tests/unit/test_cobol_parser.py`), using this finding's own nested-in-`IF` repro.

`_parse_generic_statement`'s operand loop stops the instant it sees any token that's a member of `STATEMENT_VERBS` — but `PERFORM` is itself in that set, so `EXIT`'s own required keyword operand is mistaken for the start of a brand-new statement.

Directly reproduced:
```cobol
           PERFORM UNTIL WS-DONE
               IF WS-FLAG = 1
                   EXIT PERFORM
               END-IF
               DISPLAY WS-FLAG
           END-PERFORM
```
`then_statements` becomes `(GenericStatement(verb='EXIT', tokens=('EXIT',)), PerformStatement(target_name=None, through_name=None, modifier_tokens=(), body=()))`, with zero diagnostics. The word "PERFORM" is preserved nowhere, and a fictitious empty-loop node appears in the tree at that source position — any hover/semantic/folding feature keyed off it would describe a loop that doesn't exist. Zero test coverage for `EXIT` at all.

### Parser-2. Purely-numeric paragraph/section names aren't recognized as headers, collapsing the whole procedure division into one anonymous paragraph — HIGH — **[reported as directly reproduced]** — **FIXED**

Fixed by widening `_word()` (the shared helper every header-detection check in this file goes through) to also return a `NUMERIC_LITERAL` token's text, not just `RESERVED_WORD`/`IDENTIFIER` — so a bare-numeric label is recognized as a header by the exact same code path an alphabetic one already was, with no separate special case needed. This fixes section headers too (`0100 SECTION.`), not just paragraph headers, since both go through `_word()`. Regression test: `test_numeric_paragraph_names_are_recognized_as_headers` (`tests/unit/test_cobol_parser.py`), using this finding's own two-paragraph repro and asserting both names parse correctly with zero diagnostics.

`_word()` returns `""` for a `NUMERIC_LITERAL` token, and header detection depends on `_word()` being truthy — so a bare-numeric paragraph label (`0100.`, a real, historically common IBM-mainframe COBOL numbering convention) is invisible to it.

```cobol
       0100.
           PERFORM 0200
           STOP RUN.
       0200.
           DISPLAY 'IN 0200'.
```
reportedly produces two misleading "Expected a statement, found '0100'"/"'0200'" diagnostics and silently merges both paragraphs into a single anonymous leading paragraph — the paragraph names are lost entirely, and `PERFORM 0200` then also fails semantic resolution since no paragraph named "0200" exists in the collapsed tree. Any file using this real, legal numbering style loses its entire procedure-division structure at once.

### Parser-3. Qualified MOVE targets (`MOVE x TO field OF group`) inject the qualifier keyword itself as a bogus target name — HIGH — **[verified — found independently by both the parser review and the semantic-analysis review; see Semantic-2 for the semantic-analysis-side confirmation of the same root cause]** — **FIXED (together with Parser-11)**

Fixed by adding an `OF`/`IN` exclusion to the target-collection loop's token-kind filter, alongside a paren-depth tracker (added for Parser-11's subscript-leak variant of this same bug — see there) that skips any identifier/reserved-word token found inside a subscript's parentheses. Since this MOVE-side fix removes the qualifier from `target_names`, it also directly closes Semantic-2 (the semantic-analysis-side false "Undefined data name: OF" this same root cause produces) with no separate semantic-layer change needed. The analogous PERFORM-side leak into `modifier_tokens` (this finding's own last sentence) is a distinct code path and is addressed separately under Semantic-6. Regression test: `test_move_qualified_target_does_not_leak_the_qualifier_keyword` (`tests/unit/test_cobol_parser.py`), using this finding's own repro.

`_parse_move`'s target-collection loop appends every token whose kind is `IDENTIFIER` or `RESERVED_WORD` into `target_names`, with no exclusion for the `OF`/`IN` qualifier keyword — so `MOVE 'X' TO CUSTOMER-NAME OF CUSTOMER-REC.` produces `target_names == ('CUSTOMER-NAME', 'OF', 'CUSTOMER-REC')`. Directly reproduced end-to-end through `analyze_compilation_unit`: this yields a false `Undefined data name: OF` ERROR on completely valid, qualified COBOL — exactly the construct qualification exists to support. The analogous `PERFORM target OF/IN section` case leaks the qualifier into `modifier_tokens` too, producing a lower-severity but still-spurious WARNING instead of an ERROR (see Semantic-6).

### Parser-4. `PERFORM ... THRU` with a missing/malformed through-target crashes the parser, and — via `compute_source_diagnostics`'s deliberate crash-swallowing — silently truncates all diagnostics for the rest of the file — HIGH — **[verified, both the crash and its downstream silent-swallowing interaction]** — **FIXED**

Fixed by guarding the through-target consumption the same way `looks_like_target` already guards the primary target above it: after consuming `THRU`/`THROUGH`, the next token is checked against the same "looks like a real name" shape (identifier, numeric-literal paragraph name, or a non-verb/non-terminator reserved word) before being consumed as `through_name`; an invalid one (EOF, a bare period) is left alone and reported via a new `"Expected a paragraph name after THRU/THROUGH."` diagnostic instead of being blindly swallowed. `through_name` simply stays `None` in that case — already a legal value (`PerformStatement.__post_init__` only validates it when non-`None`), so no crash, and no real statement terminator gets eaten. Regression tests: `test_perform_thru_missing_target_does_not_crash` (the EOF case that used to raise uncaught), `test_perform_thru_period_does_not_swallow_the_terminator` (the period case, now correctly diagnosed as malformed rather than silently corrupting the token stream) — both in `tests/unit/test_cobol_parser.py`.

`parser.py` (the THRU/THROUGH branch of `_parse_perform`) unconditionally consumes whatever token follows `THRU` with no guard, unlike the equivalent, correctly-guarded handling elsewhere in the file (e.g. PROGRAM-ID). Directly reproduced two ways:
- Source ending right after `PERFORM PARA-A THRU` (nothing before EOF): `through_name` becomes the empty string from the EOF token, and `PerformStatement.__post_init__`'s own non-empty-string validation raises `ValueError: Perform statement through name must not be empty.` — confirmed to propagate all the way out of `parse_cobol_tokens()` uncaught.
- `PERFORM PARA-A THRU.` (period immediately after THRU): the terminating period is silently consumed as if it were the through-name text, producing `PerformStatement(..., through_name='.')` with zero diagnostics and the real statement terminator gone from the token stream.

Critically, I traced this further myself: `compute_source_diagnostics` (`source_diagnostics.py`, the actual function the live editor's Problems panel and diagnostic underlines are built on) wraps every pipeline stage in a bare `except Exception: return tuple(diagnostics)` specifically so "a crash at any stage just truncates the diagnostic list there rather than breaking the editor" (its own docstring). Confirmed by direct execution: calling `compute_source_diagnostics` on the crash-triggering source above returns `()` — not an error, not a partial diagnostic list, nothing. The parser crash is real, but its actual live-editor consequence is worse than a visible crash: every diagnostic for the rest of the file silently disappears, with no signal to the user that anything went wrong, the moment they type an entirely ordinary, momentary mid-edit state (`PERFORM x THRU` before finishing the through-target name).

### Parser-5. Long sequential `IF ... ELSE IF ...` chains can exceed Python's recursion limit and crash with `RecursionError` — MEDIUM — **[verified: confirmed 300 links parses fine, 350 links raises under the default recursion limit]** — **DEFERRED**

Not fixed. `_parse_if` recurses through the statement-list parser for each `ELSE IF` link; fixing this properly means rewriting the IF/ELSE-IF chain into an iterative loop (an explicit stack rather than the call stack) without changing the AST shape any existing consumer (semantic analysis, folding, outline, hover) depends on — a real, invasive rewrite of one of the parser's more intricate recursive functions, not a scoped patch, and one that's easy to get subtly wrong around this codebase's own period-based implicit-termination propagation (`_sentence_terminated`). Given the risk of introducing a quiet correctness regression in exchange for raising Python's practical ceiling from ~300 links to some larger-but-still-finite number, this was left as a documented, known limit rather than attempted under this pass's time budget.

`_parse_if` recurses through the statement-list parser for each `ELSE IF` link with no iterative rewrite and no depth guard. A 300–400-branch sequential code/state dispatch chain is a realistic size for long-maintained or generated legacy COBOL (product/state/tax-code tables), not an adversarial input.

### Parser-6. The synthetic "leading unnamed paragraph"'s span wrongly starts at the enclosing division/section header, not its own first statement — MEDIUM — **[verified]** — **FIXED**

Fixed in both places this construction happens (`_parse_procedure_division`'s leading paragraph and `_parse_procedure_section`'s leading paragraph) by using `leading_statements[0].span.start` instead of the division/section header's own captured `start`. Regression test: `test_leading_paragraph_span_starts_at_its_first_statement` (`tests/unit/test_cobol_parser.py`), asserting the paragraph's span start now matches its first statement's and differs from the enclosing procedure division's own span start.

Both the procedure-division and procedure-section leading-paragraph construction capture their span's `start` from the position at the very beginning of the enclosing parse function (the `PROCEDURE`/section-name token) rather than the first leading statement. Confirmed: for a two-statement leading paragraph, `paragraphs[0].span` is byte-for-byte identical to the whole `procedure.span`, meaning any "select this node's text"/fold-this-paragraph feature would wrongly include the literal `PROCEDURE DIVISION.` header text.

### Parser-7. The obsolete `STOP literal` form is silently reclassified as an ordinary `StopRunStatement` with the literal discarded — LOW/MEDIUM — **[verified as currently latent — no consumer distinguishes the two today]** — **FIXED**

Fixed by giving `StopRunStatement` an `operand_tokens: tuple[Token, ...] = ()` field (mirroring `DisplayStatement`'s existing field of the same name/shape) and having `_parse_stop_run` collect its trailing tokens into it instead of discarding them via a bare consuming loop. A plain `STOP RUN.` now simply has an empty `operand_tokens` tuple, identical in observable behavior to before for the common case; `STOP 'OPERATOR HALT'.` now retains the literal for any future consumer that wants to distinguish the two forms. Regression tests: `test_stop_literal_retains_its_operand_tokens`, `test_stop_run_has_no_operand_tokens` (`tests/unit/test_cobol_parser.py`).

`_parse_stop_run` enters unconditionally on the verb `STOP` and only optionally consumes `RUN`; any trailing operand is swallowed and discarded by the residual-consumption loop. `STOP 'OPERATOR HALT'.` parses with zero diagnostics into a plain `StopRunStatement`, indistinguishable from a real `STOP RUN` — currently harmless since nothing treats `StopRunStatement` specially yet, but a real gap for any future "guaranteed program termination"/unreachable-code analysis.

### Parser-8. Duplicate/conflicting data-description clauses on one item (two `PIC`s, two `VALUE`s) are accepted with no diagnostic — LOW — **[verified]** — **FIXED**

Fixed narrowly, matching exactly what this finding reported: a new `_check_duplicate_data_clauses` pass over one data item's already-collected clauses flags a second `PIC`/`PICTURE` (true COBOL synonyms of the same clause) or a second `VALUE`/`VALUES` with an ERROR diagnostic. Deliberately not generalized to every clause keyword in `_DATA_CLAUSE_KEYWORDS` — several of those (`COMP`/`COMP-1`.."5"/`BINARY`/`PACKED-DECIMAL`/`DISPLAY` as USAGE variants) aren't synonyms of each other and repeating a *different* one isn't the same category of mistake as repeating the identical clause, so aliasing them together risked false positives outside this finding's own scope. Regression tests: `test_duplicate_pic_clause_is_diagnosed` (this finding's own two-PIC-two-VALUE repro), `test_single_pic_and_value_clause_is_not_flagged` (`tests/unit/test_cobol_parser.py`).

The clause-parsing loop just appends every clause with no uniqueness check; downstream, `debugger/service.py`'s PICTURE/USAGE resolution iterates in order with no `break`, so the *last* duplicate silently wins — deterministic, but silently accepting genuinely invalid COBOL (two `PIC` clauses on one entry) with zero diagnostic at parse time. Re-verified end-to-end: `01 WS-X PIC 9(3) PIC X(10) VALUE 1 VALUE 2.` parses with zero diagnostics into 4 retained clauses, and running it through `debugger/service.py:resolve_picture_and_usage` confirmed the last (alphanumeric) `PIC` silently wins over the first (numeric) one.

### Parser-9. `EXIT PERFORM` written directly in a loop body (not nested in an `IF`) eats the enclosing loop's real `END-PERFORM`, corrupting every statement after it in the paragraph — HIGH — **[verified]** — **FIXED (same fix as Parser-1)**

The `_parse_exit` fix described under Parser-1 above resolves this too, since it eliminates the phantom `PerformStatement` construction entirely — there's no longer a second, inner PERFORM parse able to consume the enclosing loop's real `END-PERFORM`. Regression test: `test_exit_perform_in_loop_body_does_not_eat_the_real_end_perform` (`tests/unit/test_cobol_parser.py`), using this finding's own repro and asserting `STOP RUN` correctly parses as a sibling statement after the loop, not inside its body.

Same root cause as Parser-1, but with unbounded blast radius rather than one corrupted node. Directly reproduced:
```cobol
           PERFORM UNTIL WS-DONE
               DISPLAY 'X'
               EXIT PERFORM
           END-PERFORM
           STOP RUN.
```
`_parse_generic_statement` splits `EXIT PERFORM` into `GenericStatement(verb='EXIT')` plus a fresh, phantom out-of-line `_parse_perform()` call starting right at the real `PERFORM` token (Parser-1's mechanism). That phantom call's own modifier loop then sees the *real* enclosing `END-PERFORM` next, matches it as its own terminator, and consumes it. The true outer loop's statement-list parser (looking for `END-PERFORM` to stop on) never finds one left, so it keeps consuming — `STOP RUN.` ends up inside the outer PERFORM's own body instead of being a sibling statement after the loop. Observed: the paragraph has exactly one top-level statement (the outer `PerformStatement`) whose `body` tuple now includes the `StopRunStatement` as a loop-body member, with zero diagnostics. If compiled/executed against this AST, `STOP RUN` would run every loop iteration instead of once after the loop — this isn't just a display/hover-quality bug, it changes program semantics for any feature built on this tree.

### Parser-10. `PERFORM <numeric-literal-target>` fails the target-detection heuristic and swallows the following real statement into a phantom inline-PERFORM body — HIGH — **[verified]** — **FIXED**

Fixed by adding `current.kind is TokenKind.NUMERIC_LITERAL` as a third alternative in `looks_like_target`'s condition, alongside the existing `IDENTIFIER`/non-verb-`RESERVED_WORD` checks — guarded by the same pre-existing `not followed_by_times` check, so `PERFORM 5 TIMES` (a literal repeat count, never a target) is correctly unaffected. Regression test: `test_perform_numeric_paragraph_target` (`tests/unit/test_cobol_parser.py`), using this finding's own repro and asserting `STOP RUN` parses as a sibling statement, not the loop's phantom body.

`_parse_perform`'s `looks_like_target` check requires an `IDENTIFIER` or qualifying `RESERVED_WORD` token — a `NUMERIC_LITERAL` target (the same legacy numeric-paragraph-name style Parser-2 already flags for headers) never matches. Directly reproduced:
```cobol
           PERFORM 0200
           STOP RUN.
```
Result: `target_name=None`, `modifier_tokens=['0200']`, and because the next token (`STOP`) is itself a statement verb, the parser takes the inline-PERFORM-with-body branch and parses `STOP RUN.` as the loop's *body* rather than a sibling statement — the paragraph ends up with exactly one top-level statement, a `PerformStatement` whose body is `(StopRunStatement(...),)`, zero diagnostics. Mechanistically distinct from Parser-2 (which is about paragraph *headers* not being recognized): this is the PERFORM statement's own target-detection heuristic failing, with a control-flow-altering consequence (`STOP RUN` becomes loop-bound) Parser-2 doesn't describe.

### Parser-11. The MOVE/PERFORM qualifier-leak (Parser-3's root cause) also injects subscript-index identifiers as bogus extra target names — MEDIUM/HIGH — **[verified]** — **FIXED (together with Parser-3)**

Fixed by adding a paren-depth counter to the MOVE target-collection loop: any identifier/reserved-word token seen while `paren_depth > 0` (i.e. inside a subscript's parentheses) is skipped rather than appended to `target_names`. A numeric subscript (`WS-TABLE(1)`) was never affected by this bug in the first place (only `IDENTIFIER`/`RESERVED_WORD` tokens were ever appended), and stays correctly excluded. Regression tests: `test_move_target_does_not_leak_a_subscript_identifier` (this finding's own repro), `test_move_target_numeric_subscript_still_excluded` (`tests/unit/test_cobol_parser.py`).

Same code as Parser-3 (`_parse_move`'s target loop) has no paren-depth tracking, only a token-kind filter. Directly reproduced: `MOVE 'X' TO WS-TABLE(I).` → `target_names == ('WS-TABLE', 'I')` — the subscript variable `I` is captured as a second MOVE target, zero diagnostics. (A *numeric* subscript, e.g. `WS-TABLE(1)`, does not trigger this, since `1` is a `NUMERIC_LITERAL` and only `IDENTIFIER`/`RESERVED_WORD` tokens get appended — so this is specific to identifier subscripts, the common case for indexed table access.) Arguably more consequential in practice than Parser-3's `OF`/`IN` case, since subscripted MOVE targets are extremely common in real COBOL table-processing code — and fixing Parser-3 by excluding `OF`/`IN` tokens would not by itself fix this; it needs paren-depth tracking as a separate change.

### Parser-12. Data item level numbers outside the legal COBOL range (01-49, 66, 77, 88) are accepted with no diagnostic — LOW — **[verified]** — **FIXED**

Fixed by validating the level token's numeric value against the legal range (1-49, or exactly 66/77/88) whenever the entry is genuinely level-numbered (`level_token.kind is TokenKind.NUMERIC_LITERAL`) and emitting an ERROR diagnostic otherwise. That guard mattered in practice: `_parse_data_item` is also reused to parse `FD`/`SD` file/sort-description entries, which use a `0` sentinel for "not level-numbered" rather than a real level number — an early version of this fix flagged every real-world `FD`/`SD` entry as invalid before the guard was added, caught immediately by the existing real-legacy-file smoke tests (`VIRTUAL-PRINTER.cbl`/`VIRTUAL-PRINTER2.cbl`) failing. Regression tests: `test_invalid_level_number_is_diagnosed`, `test_valid_level_numbers_are_not_flagged` (covering 01, 05, 66, and 88 together) — `tests/unit/test_cobol_parser.py`.

`_at_level_number` only checks that the token is a non-negative integer literal, with no range check; `DataItemNode.__post_init__` only rejects negative level numbers. ## Editor-facing services (`navigation.py`, `hover.py`, `outline.py`, `folding.py`, `rendering.py`, `diagnostics.py`, `source_diagnostics.py`, `quick_fixes.py`, `signature_help.py`, `task_list.py`)

### Editor-Facing-1. Quick Fix silently no-ops on a FIXED-format line with trailing content past column 72 — HIGH — **[reported as directly executed and reproduced]** — **FIXED**

Fixed by computing the insertion column from the FIXED-format content area's own real content (columns 8-72, trailing whitespace within that window trimmed off) instead of the raw physical line length — always at or before column 72 by construction, so the fix can never land in the sequence-number/reference area the lexer never reads. If the content area is already completely full with no room for the closing quote, `compute_quick_fix` now returns `None` rather than offering a fix that can't actually help. `compute_quick_fix` gained a `source_format` keyword (defaulting to `FIXED`, this codebase's existing implicit assumption throughout) so FREE-format callers keep the simpler raw-line-length behavior, which has no column ceiling to respect. Regression test: `test_quick_fix_clamps_to_the_fixed_format_content_area` (`tests/unit/test_language_quick_fixes.py`), which first caught an off-by-one in an earlier version of this fix (clamping to column 73, one column past the actual last-read column) before landing on the correct trimmed-content approach.

`compute_quick_fix` inserts its closing quote at `len(line_text) + 1` — the end of the *raw* line — but the FIXED-format lexer only ever scans columns 8–72 as program text; anything from column 73 onward (the classic sequence-number area) is never read. If the raw line has trailing content past column 72, the fix's insertion point lands outside the window the lexer reads at all, so applying the "fix" leaves the diagnostic completely unchanged — appearing to succeed while doing nothing.

### Editor-Facing-2. Quick Fix's position math uses raw source columns while the diagnostic it's fixing was computed against a tab-expanded line — HIGH — **[reported as directly executed and reproduced; this is the newly-confirmed second half of Lexer-2 above]** — **DEFERRED (same reasoning as Lexer-2)**

Not fixed, for the identical reason Lexer-2 above is deferred: a real fix needs a raw (non-expanded) column threaded alongside the existing tab-expanded one through `Token`/`SourceSpan` and every consumer, which is a cross-cutting API change, not a scoped patch to this one file. The practical exposure is reduced by the same Phase 3 mitigation (typed tabs become spaces at the input boundary when `insert_spaces` is enabled, the default) — the residual gap is specifically a file already containing literal tabs from another source.

When a tab precedes the unterminated literal's opening quote on that line, the raw index no longer lines up with the expanded-column position the diagnostic actually points at, the character-match check fails, and `compute_quick_fix` returns `None` — no fix offered at all for a legitimately fixable diagnostic.

### Editor-Facing-3. Nested `FUNCTION` calls always resolve signature help to the outermost function, never the one the cursor is actually inside — MEDIUM — **[reported as directly executed and reproduced]** — **FIXED**

Fixed by no longer returning on the first match: the scan now keeps going and keeps overwriting its "best" answer with each subsequent match that still contains the cursor. Since the token stream is scanned in source order and any nested FUNCTION call's parens are, by construction, strictly inside its enclosing call's, a later-found containing match is always at least as deeply nested as any earlier one — so simply keeping the *last* match found is equivalent to preferring the innermost, with no explicit span-width comparison needed. Regression test: `test_signature_help_prefers_the_innermost_nested_function_call` (`tests/unit/test_language_signature_help.py`), using this finding's own repro.

The scan returns on the *first* `FUNCTION` token whose paren range contains the cursor, scanning in source order — since an outer call's parens always fully enclose any nested call's parens, the outer match is found first and the function returns immediately without checking for a more specific inner match. `MOVE FUNCTION UPPER-CASE(FUNCTION TRIM(WS-NAME)) TO WS-RESULT` with the cursor on `WS-NAME` returns signature help for `UPPER-CASE`, not `TRIM` — the function the cursor is literally sitting inside the arguments of. Not covered by the existing signature-help tests (which only nest grouping parens, not nested FUNCTION calls).

### Editor-Facing-4. Task List's word-boundary regex treats `-` as a boundary, false-flagging tag words embedded in hyphenated COBOL identifiers — MEDIUM — **[reported as directly executed and reproduced]** — **FIXED**

Fixed by replacing the plain `\b(...)\b` pattern with lookbehind/lookahead assertions that exclude `-` from both sides, alongside the ordinary word characters `\b` already excludes — so a tag word directly flanked by a hyphen on either side (as in a COBOL hyphen-delimited identifier reference) no longer matches as a standalone tag, while a genuinely standalone tag next to whitespace/punctuation still does. Regression tests: `test_does_not_match_a_tag_embedded_in_a_hyphenated_identifier` (this finding's own repro), `test_still_matches_a_real_tag_next_to_punctuation` (`tests/unit/test_language_task_list.py`).

The `\b(TODO|FIXME|HACK|XXX)\b` pattern correctly rejects a tag that's merely a substring of a longer word (`TODOLIST`, `HACKATHON`), but `-` counts as a non-word character for `\b`, and COBOL identifiers are hyphen-delimited — so a hyphen-flanked segment matching a tag word is treated as a whole word. `* See WS-HACK-FLAG for details on this switch.` produces a false `HACK` task-list entry despite the comment containing no actual task marker, just a reference to a data name.

### Editor-Facing-5. Inconsistent "nothing to fold" guard: an empty `IF`/`END-IF` still gets a fold range, but an empty out-of-line `PERFORM` doesn't — LOW — **[reported as directly executed and reproduced]** — **FIXED**

Fixed by making `IfStatement` (guarded on `then_statements or else_statements` being non-empty) and `EvaluateStatement` plus its individual `WHEN` branches (each guarded on having any branch/its own statements) all consistent with `PerformStatement`'s existing "don't fold zero content" behavior, rather than picking a direction and rewriting PERFORM's — the more conservative behavior was already correct, this just extends it uniformly. Regression test: `test_empty_if_produces_no_fold_range` (`tests/unit/test_language_folding.py`), using this finding's own repro.

`PerformStatement` fold ranges are only added when the body is non-empty, but `IfStatement`/`EvaluateStatement` fold ranges are added unconditionally regardless of whether their branches contain anything — `IF 1 > 0\nEND-IF` (empty in both branches) still yields a fold range hiding zero lines of content, inconsistent with the deliberate empty-PERFORM exclusion in the same file. Re-audit found the same asymmetry extends to empty `WHEN` branches inside `EVALUATE` too (same unconditional add, `folding.py:234-238`) — not a separate bug, just a wider blast radius for the same root cause.

### Editor-Facing-6. Signature help never fires while a `FUNCTION` call's parenthesis is still unclosed — HIGH — **[reported as directly executed]** — **FIXED (together with Editor-Facing-3)**

Fixed by treating an unclosed call as a match whenever the cursor is at or after the open paren's own end (no upper bound to check against, since there's no closing paren yet), instead of skipping it entirely. Combined with Editor-Facing-3's fix (return the *last* qualifying match, not the first): an unknown/unrecognized outer call wrapping a known inner one no longer suppresses the inner match either, since a missing-signature outer candidate no longer short-circuits the scan. Regression test: `test_signature_help_fires_while_the_call_is_still_unclosed` (`tests/unit/test_language_signature_help.py`), using this finding's own repro.

`_find_matching_close_paren` must find a balanced closing paren before any match is considered; if it returns `None`, the scan just skips past that `FUNCTION` entirely. Directly reproduced: with source ending `MOVE FUNCTION UPPER-CASE(` (cursor right after the open paren — the user has typed the function name and opened the argument list but hasn't finished it), `compute_signature_help` returns `None`. The identical call with the closing paren already present (`UPPER-CASE()`) returns the correct signature. This inverts signature help's primary use case: the moment it's most valuable — mid-way through typing the argument list — is exactly the moment this returns nothing. No existing test exercises an unclosed/in-progress call. Related, and folded into the same root cause rather than filed separately: once a (possibly wrong, per Editor-Facing-3) outer match is picked, if that outer function name isn't in the known intrinsics table the function returns `None` outright instead of falling back to check for a more specific, known inner match — so an unknown outer call wrapping a known inner one suppresses signature help entirely.

### Editor-Facing-7. Go-to-definition, hover, and find-references ignore the data-name/procedure-name namespace separation that semantic analysis itself correctly maintains — MEDIUM — **[reported as directly executed]** — **FIXED**

Fixed with a new shared `navigation._reference_kind_at` helper, consulted by `find_definition`, `find_references`, and `compute_hover` alike, that determines whether the specific identifier occurrence under the cursor is a data-name or procedure-name usage before deciding which symbol table to prefer — checked two ways, in order: (1) is the cursor sitting exactly on a symbol's own declaration (a procedure symbol's span starts precisely at its name token, so this is an exact position match; a data item's span starts at its *level number* instead — a separate, already-documented AST precision limit — so this check uses "same line as the item's declaration" instead of an exact position match for data items); (2) if not on a declaration, what the immediately preceding significant raw token implies (`TO`/`FROM`/`BY` imply a data-name context; `PERFORM`/`THRU`/`THROUGH` imply a procedure-name context). When neither check yields an answer, behavior falls back to the original procedure-first default, preserving existing behavior for the ordinary non-colliding case.

The first implementation attempt used exact-position matching against `semantic_result.data_references`/`procedure_references` entries instead of step (2) above, and failed its own regression test: `_resolve_data_names`/`_resolve_procedure_name` record a MOVE or PERFORM target's reference at the *whole statement's* start position (`statement.span.start`), not the specific target token's own position — a separate, pre-existing AST precision limit this tracker's own intro paragraph for Phase 4 already calls out ("a MOVE-target diagnostic can only point at the statement's start, not a specific target name"). Exact-position matching against those recorded references therefore could never succeed for the exact MOVE-target case this finding is about, silently falling through to the old (wrong) default every time. Caught by running the new regression tests before considering this fixed, not just trusting the logic on paper. Regression tests: `test_find_definition_on_a_move_target_resolves_the_data_item_not_the_paragraph`, `test_find_definition_on_a_perform_target_resolves_the_paragraph_not_the_data_item`, `test_find_references_on_a_move_target_excludes_the_paragraph_usages` (`tests/unit/test_language_navigation.py`), using this finding's own name-collision repro.

Real COBOL keeps procedure-names (paragraphs/sections) and data-names in separate namespaces — a paragraph and a data item are legally allowed to share a name — and `semantic.py` itself respects this: `_resolve_data_names` only ever populates `data_references`, `_resolve_procedure_name` only ever populates `procedure_references`, correctly separated by actual usage context. But `find_definition` and `compute_hover` both check `find_procedure_symbol(name)` first, unconditionally, and return immediately on a hit — with no regard for whether the cursor's identifier is actually being used in a data-name context.

Directly reproduced: a program with data item `01 WS-COUNT` and a same-named paragraph `WS-COUNT.`, with `MOVE 5 TO WS-COUNT.` (a MOVE target — structurally guaranteed to be a data name). Placing the cursor exactly on that `WS-COUNT` token: `find_definition` returns the **paragraph**, not the data item; `compute_hover` reports `kind='paragraph'`. `find_references` compounds this by merging both symbols' locations into one "references" result — the data item's own definition, the MOVE usage, a PERFORM usage of the paragraph, and the paragraph's own definition all come back together, mixing two conceptually unrelated symbols because the lookup is purely name-string-based with no context disambiguation. No existing test has a paragraph/data-item name collision.

### Editor-Facing-8. Merged source diagnostics are not sorted by position — LOW — **[reported as directly executed]** — **FIXED**

Fixed with a final `diagnostics.sort(key=lambda diagnostic: (diagnostic.position.line, diagnostic.position.column))` before returning, relying on Python's stable sort to preserve stage order (lex, then parse, then semantic) as the tiebreak for two diagnostics that land at the identical position. One existing GUI test (`test_current_diagnostics_converts_to_compiler_diagnostic`) had to be updated: its fixture source was missing IDENTIFICATION DIVISION entirely, so a parse-level "Expected IDENTIFICATION DIVISION" diagnostic at column 8 now correctly sorts before the lex-level "not terminated" diagnostic at a later column on the same line — the test's original assumption that the lex diagnostic would always be `diagnostics[0]` was itself an artifact of the very ordering bug this finding describes, not a real requirement; it now checks for both diagnostics' presence and every diagnostic's `source_path` without assuming a specific index. Regression test: `test_diagnostics_are_sorted_by_source_position` (`tests/unit/test_language_source_diagnostics.py`), using this finding's own early-parse-error/later-lex-error repro shape.

`compute_source_diagnostics` builds its result by concatenating each stage's diagnostics in stage order (lex, then parse, then semantic) with no final sort — unlike `compute_fold_ranges`, which explicitly sorts its own output by `start_line`. Directly reproduced: source with an early parse error (line 2) and a later lex error (line 4) returned diagnostics in the order `[line 4, line 2]` — out of document order. Any Problems-panel consumer that trusts this tuple's order directly (rather than re-sorting itself) would display diagnostics out of source order. Related, minor: there's no dedicated test file for `diagnostics.py` itself (the `LexDiagnostic`/`ParseDiagnostic` dataclasses); it's only exercised incidentally via other test files.

**Checked and found correct:** `identifier_at` boundary math (one-before-start, one-after-end, mid-hyphen) is correct; symbol-table lookups throughout `navigation.py`/`semantic.py` are consistently case-insensitive; `signature_help.py`'s paren-depth counter correctly ignores parens inside string-literal arguments (the lexer emits a literal as one token) and correctly handles 3+ levels of nesting; `render_clause_tokens` cannot see a stray `COMMENT` token inside a clause's token list, since the parser cursor filters comments out before clause construction; `compute_source_diagnostics` correctly surfaces every stage's diagnostics for whitespace-only, comments-only, and severely malformed source (aside from the Parser-4 crash-swallowing interaction recorded above) with no duplicate diagnostics observed for one root cause (ordering aside — see Editor-Facing-8); no `hover.py` documentation-table entry references a word absent from the reserved-word set; `ProcedureDivisionNode.paragraphs`/`sections` and `outline.py`/`folding.py`'s walks of them keep unsectioned top-level paragraphs and each section's own paragraphs in disjoint lists, so there's no double-counting/duplicate fold-or-outline-entry risk from that structure.

## Cross-cutting observations (Phase 4)

- **The same `OF`/`IN`-qualifier bug was independently rediscovered by two separate review passes** (Parser-3 and Semantic-2) — one by reading the parser's target-collection loop, the other by tracing a false diagnostic back through semantic analysis to the same root cause. This is the second time in this tracker two independent passes have converged on the identical bug (the first was Phase 2's drive-relative-path validator gap) — a strong signal that convergent findings like these are genuinely structural, not reviewer error, and that COBOL's `OF`/`IN` qualification syntax is a systematically under-handled feature across this entire pipeline (MOVE targets, PERFORM targets, and by extension probably any other statement that accepts a qualified data name). The re-audit found this same unguarded-loop root cause is broader still — it also leaks subscript-index identifiers (Parser-11), not just qualifier keywords.
- **`compute_source_diagnostics`'s deliberate blanket exception handling is a double-edged design.** It successfully prevents any single parser/lexer/semantic bug from crashing the editor outright (a genuinely good defensive choice for a live-typing IDE) — but it also means every bug found in this phase that raises an exception (Parser-4, and potentially others not yet found) degrades silently rather than visibly: the user sees fewer diagnostics than they should, with no signal that anything went wrong, rather than an obvious error they could report. The lexer's own tab/comment-interruption bugs are the "wrong diagnostic" flavor of this problem; Parser-4 is the "no diagnostics at all past this point" flavor, which is strictly worse — and the re-audit confirmed it's worse still: diagnostics already found *before* the crash point in the same file are discarded too, not just hypothetical ones after it.
- **Legacy-COBOL-specific input keeps being the thing that breaks this pipeline**: numeric paragraph names (Parser-2, and now also Parser-10's PERFORM-target variant of the same style), D-indicator debug lines (Lexer-5), and long sequential IF-ELSE dispatch chains (Parser-5) are all real, historically common patterns in exactly the kind of legacy mainframe source this IDE exists to modernize — these aren't exotic edge cases, they're the target user's actual code. (Semantic-8's original SCREEN SECTION example has been retracted — see its correction above; it was never a real instance of this pattern, since SCREEN SECTION has always parsed correctly.)
- **Every one of the "silent, zero-diagnostic" findings in this phase (Lexer-1, Parser-1, Parser-2, Parser-4, Parser-7, Parser-8, Semantic-3, and now Lexer-10, Parser-9, Parser-10, Parser-11 from the re-audit) is more dangerous than a visible error would be**, for the same reason repeatedly noted throughout this tracker: a user has no way to discover their COBOL was misinterpreted unless they already suspect it and go looking.
- **NEW (re-audit): any statement verb without a dedicated AST node is a systematic blind spot for procedure-vs-data namespace correctness.** `EXIT` (Parser-1/9), `GO TO` and `ALTER` (Semantic-11), and by extension any future verb added the same way, all fall through to `_parse_generic_statement`/`GenericStatement`, whose only downstream semantic treatment (`_resolve_identifier_tokens`) checks exclusively against the *data* symbol table — there is no code path from a `GenericStatement` into `find_procedure_symbol` at all. This isn't four unrelated bugs; it's one architectural gap (bare-verb statements have no first-class representation of "this operand is a procedure name") surfacing every time a verb takes a paragraph/section-name operand without its own parser rule.
- **NEW (re-audit): this phase's own reviewing process caught and corrected a real error in its own prior output** (Semantic-8, above) — a useful reminder that "already audited" findings in a fast-moving codebase-review effort like this one are worth periodically re-verifying against actual execution, not just trusted as permanently settled once written down.

## Priority items (highest impact across Phase 5)

1. **Build Project derives every compiled file's output path from the source filename alone, discarding its directory** — two source files with the same base name in different folders (a realistic copybook/utility-naming pattern) silently overwrite each other's compiled binary, with the build reporting both as `succeeded` and no warning that anything collided. 6. **Whitespace-padded PATH/STRING configuration values (a leading/trailing space in a pasted compiler path, for instance) pass profile validation but are never trimmed before use**, so a configured compiler that would otherwise resolve correctly is instead silently treated as "not found" by toolchain discovery. ### CompilerAbstraction-1. Whitespace-padded PATH/STRING configuration values pass validation but are never trimmed before use — MEDIUM — **[verified]** — **FIXED**

Fixed at the point of use rather than at validation time (the validator's own emptiness check is unaffected): `services/toolchains.py::GnuCobolToolchainService._compiler_path` now strips the resolved `compiler_path` value before constructing the `Path`, and the `process_environment` loop over `_GNUCOBOL_ENVIRONMENT_CONFIGURATION_KEYS` (`config_directory`/`copy_directory`/`library_path`) now strips each configured value before assigning it into the environment mapping, matching the defensive re-stripping `custom_local_diagnostics.py` already did elsewhere. ### CompilerAbstraction-2. Environment-variable override names are never case-normalized; a differently-cased override silently fails to override the ambient environment — MEDIUM — **[verified]** — **FIXED**

Fixed in `services/toolchains.py::process_environment`'s override-merge loop via a new module-level `_find_case_insensitive_key` helper (mirroring the existing, already-established pattern in `services/project.py::_merge_environment`/`_find_case_insensitive_key` from an earlier Phase 2 fix): before inserting an override, it now scans the in-progress environment dict for any existing key that matches case-insensitively and deletes it first, so a `{"Path": "..."}` override replaces the ambient `PATH` entry outright instead of coexisting alongside it. The self-contradictory-case-variant-overrides half of this finding (a single profile saved with both `PATH` and `Path` keys) is unaffected by this fix and remains a latent gap — profile-level override dicts are still validated only for string types, not internal case-collisions. Regression test: `test_environment_override_replaces_a_differently_cased_base_key` (`tests/unit/test_configured_toolchains.py`).

`providers/models.py` (`_freeze_environment`) validates only that names/values are strings, no case-collision detection. `services/toolchains.py::process_environment` builds a plain `dict` from `os.environ`/`base_environment` and calls `.update(profile.environment_overrides)` — but Windows environment variables (and `subprocess`'s environment block) are case-insensitive in practice, while a Python `dict` is case-sensitive. Directly reproduced: with a real ambient `PATH` and a profile override `{"Path": "Z:/overridden/bin"}`, the resulting dict ends up with **both** `"PATH"` and `"Path"` keys — the override never actually replaces the original entry, and which one a spawned child process observes on Windows is implementation-defined. ### CompilerProcess-1. Build Project derives output paths from the source filename alone, so same-named files in different directories silently clobber each other's compiled binary — HIGH — **[verified]** — **FIXED**

Two files with the same base name in different source folders now compile to distinct, non-colliding output paths. Regression test: `test_build_handler_keeps_same_named_sources_in_different_directories_separate` (`tests/unit/test_gui_build_commands.py`) — reproduces the exact `moduleA/UTILS.cbl` / `moduleB/UTILS.cbl` scenario from this finding and asserts both compiled outputs exist independently.

`gui/build_commands.py`'s `create_build_project_handler` compiles every discovered `.cbl`/`.cob` file across the whole project tree into `output_directory / source_file.stem` — the source's own subdirectory is discarded entirely. Two files with the same base name in different folders (a realistic copybook/utility-naming pattern, e.g. `moduleA/UTILS.cbl` and `moduleB/UTILS.cbl`) collide on the exact same output path. Reproduced end-to-end with a real subprocess stub compiler: both files compile, the Output panel reports **both** as `succeeded` and shows `Build complete: 2 file(s) compiled.`, but only one file exists on disk afterward, containing only the second file's content — the first file's binary is silently overwritten with no warning, error, or diagnostic of any kind.

### CompilerProcess-2. A GnuCOBOL compile that times out mid-diagnostic-line crashes with an uncaught `ValueError` instead of returning a `TIMED_OUT` result — HIGH — **[verified]** — **FIXED**

Fixed by skipping rather than emitting the malformed diagnostic: both `gnucobol_diagnostics.py::parse_gnucobol_diagnostics` and `custom_local_diagnostics.py::parse_custom_local_diagnostics` now check `if not message.strip(): continue` immediately after extracting the message (and any trailing warning code) from a matched line, before ever constructing a `CompilerDiagnostic`. A truncated line that backtracks into a whitespace-only "message" is now silently dropped instead of tripping `CompilerDiagnostic`'s own non-empty-message invariant and crashing `compile()` uncaught. Regression tests: `test_truncated_diagnostic_line_producing_empty_message_is_skipped` in both `tests/unit/test_gnucobol_diagnostics.py` and `tests/unit/test_custom_local_diagnostics.py` — each reproduces the exact truncated-line shape from this finding (`"program.cob:5: error:  "`, two trailing spaces) alongside a well-formed second line, and confirms only the well-formed diagnostic survives instead of the parse crashing.

`GnuCobolCompiler.compile` unconditionally parses diagnostics from whatever output was captured, for every status branch including `TIMED_OUT`. `subprocess.TimeoutExpired`'s captured `stdout`/`stderr` is whatever partial bytes were caught before the kill, and can end mid-line. If truncation lands right after a diagnostic's `: severity:` prefix, the diagnostic-line regex's lazy message group can still match via backtracking (capturing a single leftover whitespace character), producing a diagnostic whose message strips down to empty — which `CompilerDiagnostic.__post_init__`'s own non-empty-message validation then rejects by raising `ValueError`, uncaught, all the way out of `compile()`. Directly reproduced by simulating a `TimeoutExpired` with output truncated right after `"prog.cob:5: error: "`: confirmed the `ValueError` escapes `compile()` uncaught. Since `build_commands.py`'s per-file loop has no try/except around `runtime.compile(request)` (only around runtime *activation*), this would abort the whole Build Project run mid-file with an unhandled exception instead of the graceful `TIMED_OUT` status every other timeout produces.

### CompilerProcess-3. Neither `gnucobol.py` nor `local_process.py` pins `encoding=` on `subprocess.run`, silently mangling UTF-8 diagnostic text into mojibake on this Windows locale — MEDIUM-HIGH — **[verified]** — **FIXED**

Fixed by adding `encoding="utf-8"` alongside the existing `text=True, errors="replace"` on the `subprocess.run` call in both `gnucobol.py::GnuCobolCompiler._invoke` and `local_process.py::invoke_local_compiler_process` — the identical fix this tracker already applied to Git's own subprocess layer (`git/process.py::invoke_git_process`, Git finding #4). Both files' `_normalize_process_output` helpers (used for the `TimeoutExpired` partial-output path) now also pass `"utf-8"` explicitly to `bytes.decode(...)` rather than relying on the implicit default, matching `git/process.py`'s equivalent helper for consistency. No dedicated non-ASCII-text regression test was added (constructing a real subprocess that writes raw UTF-8 bytes under a non-UTF-8 locale isn't practical to assert deterministically in a fast unit test, the same reasoning already noted for the analogous Git fix); the existing `test_timeout_returns_partial_captured_output` (`tests/unit/test_gnucobol_compiler.py`) and `test_timeout_becomes_timed_out_result` (`tests/unit/test_local_compiler_process.py`) both continue to pass unchanged, confirming the added `encoding=` parameter doesn't alter behavior for the ordinary/malformed-byte cases they already cover.

Both files call `subprocess.run(..., text=True, errors="replace", ...)` with no explicit `encoding=`, so decoding falls back to the system's preferred encoding (`cp1252` on this machine) — exactly the bug shape this tracker already found and **fixed** for `invoke_git_process` (Git finding #4), reintroduced independently here. Directly reproduced with a real child process writing raw UTF-8 bytes for accented text (plausible verbatim output from a UTF-8-saved `.cob` source, since this IDE defaults documents to UTF-8): decoding without a pinned encoding produced the wrong codepoints (mojibake), while UTF-8-pinned decoding matched the expected text exactly. Notably worse than the visible corruption in Git's version of this bug: `cp1252` can decode any single byte without raising, so `errors="replace"`'s `U+FFFD` marker never even triggers — the corruption is silent, plausible-looking mojibake with no visible sign anything went wrong.

### CompilerProcess-4. `gnucobol_diagnostics.py` only strips the trailing `[-Wxxx]` code from `warning:` lines, but real GnuCOBOL 3.2.0 also emits it on `note:` lines — MEDIUM — **[verified against real cobc 3.2.0]** — **FIXED**

Fixed by widening `_extract_warning_code`'s severity gate from `WARNING` only to `WARNING` and `NOTE`, matching `custom_local_diagnostics.py`'s own equivalent helper, which already strips the bracket for every severity uniformly. A `note:` line's trailing `[-Wtruncate]` marker is now correctly separated into `code`, not left glued onto the message text. Regression test: `test_note_severity_strips_trailing_warning_code` (`tests/unit/test_gnucobol_diagnostics.py`).

The warning-code-stripping helper is gated to only run for `WARNING`-severity diagnostics. Verified against a real GnuCOBOL 3.2.0 install (`cobc.exe`, discoverable in the reviewing sandbox via this codebase's own toolchain-discovery logic): compiling a real truncating `MOVE` with `-Wall` produces one `warning:` line plus two accompanying `note:` lines, all three carrying a trailing `[-Wtruncate]` marker. The warning is parsed correctly (code extracted, bracket stripped), but both notes come out with the bracket left glued onto the message text and `code=None` — polluting every note the Problems panel would show alongside a routine warning (this single truncation warning alone produced two such notes). `custom_local_diagnostics.py`'s equivalent helper is not severity-gated and strips the bracket for every severity uniformly — the two near-duplicate files disagree on this exact behavior, and the GnuCOBOL-specific one is the one that's wrong against its own real compiler's actual output.

### CompilerProcess-5. Build Project's entire per-file compile loop runs synchronously on the Qt GUI thread — HIGH — **[confirmed]** — **DEFERRED**

Not fixed. A real fix means moving the per-file compile loop onto a `QThread`/worker object that emits Qt signals for per-file progress and final results, rewiring `output_widget.append_line`/`problems_widget.set_diagnostics` to receive those updates via signal/slot connections (the only thread-safe way to touch widgets from a worker thread) instead of the direct synchronous calls the handler makes today, and adding a way to cancel an in-flight build -- a genuine feature addition (background execution + cancellation UI), not a scoped bug patch, and one with real architectural weight: `create_build_project_handler` returns a plain `CommandHandler` callable that today runs-to-completion and returns, so introducing async execution changes its contract for every caller. It would also invalidate the testing approach every existing test in `test_gui_build_commands.py` (and the new CompilerProcess-1 regression test added alongside it this pass) depends on: each calls the handler directly and asserts final state immediately with no event-loop pump, which only works today because the call is genuinely fully synchronous -- making it async would require rewriting this entire test file to pump the Qt event loop or wait on a completion signal instead. Given the scope of a real fix (new threading infrastructure, a cancellation affordance, and a full rewrite of the build-command test suite) versus this pass's scope of targeted, verifiable bug fixes, this is deferred alongside this tracker's other architecturally-risky findings (Lexer-2/5/8, Parser-5, Editor-Facing-2) rather than attempted as a partial/unsafe patch. The practical impact remains real and unmitigated: a menu-triggered build still freezes the whole application for the sum of every file's compile time, with no way to cancel.

`create_build_project_handler`'s inner loop calls `runtime.compile(request)` directly for every source file, bottoming out in a blocking `subprocess.run` (up to the configured timeout, per file). Traced the full dispatch chain — menu/toolbar action → `CommandService.execute` → the handler itself — and found no `QThread`/`QRunnable`/`QtConcurrent`/`moveToThread`/`processEvents` anywhere in it (confirmed via a full-tree grep with zero matches). Every existing test in `test_gui_build_commands.py` calls the handler directly and asserts final state immediately with no event-loop pump — which only works because the call is genuinely fully synchronous, corroborating the finding rather than merely being consistent with it. Consequence: a real menu-triggered build freezes the whole application for the sum of every file's compile time, with no way to cancel, and per-file "Compiling X..." output lines are queued but not actually painted until the entire loop finishes and control returns to the Qt event loop.

### CompilerProcess-6. `GnuCobolCompiler.compile()` has no per-call timeout override — MEDIUM — **[confirmed]** — **FIXED**

Fixed by adding an optional `timeout_seconds: float | None = None` keyword parameter to both `GnuCobolCompiler.compile()` and its internal `_invoke()`, threaded through to `subprocess.run`'s `timeout=`; when omitted, it falls back to `self.timeout_seconds` exactly as before, so every existing caller is unaffected. Mirrors the identical per-call override pattern this tracker already added to the Git service layer (Git finding #5). The override is validated positive the same way the instance-level default already is. Regression tests: `test_per_call_timeout_overrides_instance_default` and `test_per_call_timeout_override_must_be_positive` (`tests/unit/test_gnucobol_compiler.py`).

`timeout_seconds` is a dataclass field fixed once at construction, with no per-call override parameter on `compile()`. The single activated compiler instance is reused for every file in a whole-project build, so one legitimately slow-to-compile file (a large legacy module, real-time antivirus scanning on a locked-down corporate machine, etc.) can't get more time without changing the global default for every other file too. The exact "single, non-overridable per-instance timeout" shape this tracker already found and **fixed** for Git (Git finding #5) — reintroduced here with no fix, and unlike Git, no settings surface exposes this value to the user at all. `local_process.py`'s lower-level custom-local invocation does not have this problem — its caller supplies `timeout_seconds` fresh on every call.

### CompilerProcess-7. Diagnostic severity recognition is a closed word-list; anything outside it is dropped entirely, not merely downgraded — LOW/MEDIUM — **[verified mechanism; real-world trigger unconfirmed]** — **FIXED**

Fixed by adding a generic fallback pattern pair (located and unlocated) to both `gnucobol_diagnostics.py` and `custom_local_diagnostics.py`, tried only after all of the existing closed-word-list patterns have already failed to match a given line — so every already-recognized severity (`error`/`fatal error`/`warning`/`note`) still resolves via the exact same pattern as before, with zero behavior change for any currently-supported line shape. A line using any other category word (a hypothetical `info:` line, or a future GnuCOBOL version's new diagnostic category) now falls through to the generic pattern instead of matching nothing, and is captured as a `DiagnosticSeverity.NOTE` diagnostic via `_parse_severity`'s existing catch-all mapping, rather than being silently dropped. Regression tests: `test_unrecognized_severity_word_still_produces_a_diagnostic` in both `tests/unit/test_gnucobol_diagnostics.py` and `tests/unit/test_custom_local_diagnostics.py`.

Every diagnostic-line regex (in both `gnucobol_diagnostics.py` and `custom_local_diagnostics.py`) requires the severity token to be literally `fatal error|error|warning|note`, case-insensitive. A line using any other category word (e.g. a hypothetical `info:` line) matches none of the patterns — including the unlocated-diagnostic fallback, which requires the same closed set — and produces zero diagnostics, not even a downgraded/miscategorized one. Directly verified the drop mechanism against a synthetic `info:`-severity line. Contrasts with this project's own predecessor codebase (`legacy/opencobolide`), whose equivalent regex used a permissive "any word" category match instead of a closed list. Real cobc 3.2.0 output sampled during this pass only ever used `error`/`warning`/`note`, so a live trigger (a localized cobc build, a future GnuCOBOL version adding a new category) couldn't be forced in this sandbox — flagged as a real, verified gap whose practical likelihood is unconfirmed.

**Checked and found correct:** no shell-injection/quoting risk anywhere in this half — both `gnucobol.py` and `local_process.py` always invoke `subprocess.run` with an argument list, never `shell=True`, so Windows argument quoting is handled automatically and correctly; Windows drive-letter paths (`C:\...`) in diagnostic lines parse correctly despite the extra colon, verified against both existing tests and real cobc 3.2.0 output; real cobc's multi-line source-context/caret output is correctly filtered out by both diagnostics parsers, verified against real (not just synthetic) compiler output; one file's compile failure does not abort the rest of the build — the loop has no early exit on failure, verified via the existing multi-file success+failure test; the build pipeline has no race conditions, since it's entirely single-threaded/synchronous (the same design that causes CompilerProcess-5's GUI freeze); `CompileRequest`/`CompileResult` invariants are correctly enforced and tested; `TimeoutExpired`/`OSError` → `TIMED_OUT`/`FAILED_TO_START` conversion is correct for the ordinary (non-crashing) case; environment merging (prepending the toolchain's `bin_directory` to `PATH` while preserving the caller's base environment) works as tested.

**Test coverage gaps:** no test verifies or documents the build command's synchronous/blocking dispatch (CompilerProcess-5, still deferred) — inherently hard to unit test for UI responsiveness, but there isn't even a lower-bar test distinguishing sync vs. async dispatch. All other gaps originally listed here (an empty/whitespace-only diagnostic message, non-ASCII/UTF-8 output, the same-basename-in-different-directories output collision, a `note:`-severity line carrying a trailing `[-Wxxx]` code) are now closed — each has a named regression test under its own CompilerProcess-N entry above. Integration tests actually executed (not skipped) during this pass, against a real, sandbox-discoverable GnuCOBOL 3.2.0 toolchain: `test_configured_gnucobol_toolchain.py`, `test_gnucobol_installation.py`, `test_gnucobol_debug_build.py` (both cases), and `test_gnucobol_variable_decoding.py` — all 5 passed for real; the real compiler was additionally driven directly outside the checked-in suite to capture genuine diagnostic text, which is what surfaced CompilerProcess-4 and upgraded several other findings from "tested against fixtures" to "verified against real output."

## Cross-cutting observations (Phase 5)

- **This phase independently reproduces two bug shapes this tracker already found and fixed in the Git service layer, in the compiler process layer instead**: unpinned subprocess output encoding (Git finding #4 / CompilerProcess-3) and a single non-overridable per-instance command timeout (Git finding #5 / CompilerProcess-6). Both are the same root pattern — this codebase's subprocess-invocation helpers were each written independently rather than sharing a common, already-hardened base — so a future subprocess integration (a third compiler provider, a VCS other than Git, anything else that shells out) should be assumed to need the same two fixes again unless a shared helper is introduced.
- **The abstraction layer (providers/runtimes/profiles) and the process-execution layer (`gnucobol.py`/`local_process.py`/`build_commands.py`) were reviewed independently by two separate passes, and both surfaced the identical underlying theme**: validation performed at profile-save time (in the abstraction layer) is weaker than validation performed at actual compile time (in the process layer) — CompilerAbstraction-1's discarded whitespace-normalization and CompilerAbstraction-7's unchecked template syntax both mean a profile can look "valid" when saved and only reveal a real problem later, with a different and less helpful error, during an actual build.
- **Every HIGH-severity finding in the process-execution half (CompilerProcess-1, -2, -5) shares the same "no visible error, or the wrong kind of error" shape already established as a recurring pattern throughout this entire tracker**: a silent file overwrite with no warning (1), a crash the user would see as an unrelated stack trace rather than a normal build failure (2), and a frozen UI with no indication *why* it's frozen or how long it'll stay that way (5) are three different failure presentations of the same underlying "the build pipeline doesn't defend against its own edge cases" gap.

# Phase 6 — Debugger

Scope: the GDB-backed debugger end to end. Three independent reviews covered (1) the Qt-independent adapter/protocol/domain-model layer — `debugger/models.py`, `debugger/mi_protocol.py`, `debugger/gdb_adapter.py` — the layer that spawns and speaks to a real `gdb --interpreter=mi2` subprocess; (2) session orchestration, GnuCOBOL symbol resolution, and COBOL value decoding — `debugger/service.py`, `debugger/gnucobol_symbols.py`, `debugger/cobol_values.py` — the most novel, custom-logic-heavy part of the whole debugger; and (3) the Debug GUI — `gui/debug_commands.py`, `gui/debug_session.py`, and the six dock-widget panels (Call Stack, Locals, Watch, Threads, Registers, Memory). A real GDB (`C:\Strawberry\c\bin\gdb.exe`) and a real GnuCOBOL 3.2.0 install (`C:\msys64\ucrt64\bin\cobc.exe`, discoverable via this codebase's own `discover_gnucobol()`) were both reachable in the reviewing sandbox, so the large majority of findings below were verified by actually compiling purpose-built `.cbl`/C fixtures with `-g -debug` and driving them through a real live GDB session via this codebase's own `GdbAdapter`/`DebuggerService`, not by reading code or existing fixtures alone.

## Priority items (highest impact across Phase 6)

1. **`read_variable` — the debugger's star feature — only works for flat, top-level elementary data items.** Any item nested inside a group/record, an OCCURS table element, a REDEFINES view, or a LINKAGE SECTION (`CALL ... USING`) parameter is completely invisible to it, because GnuCOBOL's generated `.c.l.h`/`.c.h` comments never mention them at all — confirmed against four separate real `cobc -g -debug` compiles. Since virtually every non-toy COBOL program organizes WORKING-STORAGE into records, this collapses the headline feature to a narrow slice of real-world COBOL. §DebuggerLogic-1/2/3/4 below. **FIXED for group members and REDEFINES views (1/3); DEFERRED for OCCURS elements and LINKAGE parameters (2/4) — cobc's own debug output has no static symbol for either, confirmed by direct inspection of the generated C, not a parsing gap this codebase can close.**
2. **Any exception raised inside a registered `on_stopped`/`on_notify`/`on_console_output` callback permanently and silently kills the GDB background reader thread**, with no visible symptom except every future command timing out after the full configured wait — directly reproduced against a real `gdb` session. §DebuggerCore-1 below (see also -2, the same crash triggerable via deeply nested MI values). **FIXED (both).**
3. **Ending a debug session any way other than a natural program exit (i.e. clicking "Stop Debugging" while paused) leaves all six debug panels showing stale data from the dead session indefinitely**, with nothing in the UI indicating the session ended; the Memory panel specifically is never cleared under *any* circumstance, including the one path that does clear the other five. Directly reproduced end-to-end against a real GDB/GnuCOBOL session. §DebugGUI-1/2 below. **FIXED.**
4. **`step_into_cobol_line`'s default 50-internal-step budget is far too small for a real `CALL`** — stepping into even a trivial two-statement subprogram measured between 51 and 500 raw GDB steps in a real repro, so this ordinary debugging action reliably fails with a raw internal error rather than landing in the callee. §DebuggerLogic-5 below. **FIXED.**
5. **Neither `gdb_adapter.py`'s subprocess pipes nor `service.py`'s `collect_local_variables`/`evaluate_watch_expressions` are hardened against realistic failure modes**: no pinned `encoding=` on the GDB subprocess (the third instance of a bug shape this tracker has now found three times independently), and only one specific exception type is caught around variable/watch reads, letting a `GdbAdapterError`/`TimeoutError` silently abort the rest of a stop's panel refresh (including the "jump to current line" step) with only a raw traceback on stderr. §DebuggerCore-3, §DebuggerLogic-6, §DebugGUI-3 below. **FIXED (all three).**

## Debugger core & MI protocol (`debugger/models.py`, `debugger/mi_protocol.py`, `debugger/gdb_adapter.py`)

### DebuggerCore-1. Any exception raised inside a registered observer callback permanently and silently kills the background reader thread — HIGH — **[verified]** — **FIXED**

Fixed by routing every callback invocation in `_dispatch` through a new `_invoke_observer` helper that wraps the call in `try/except Exception: pass`, isolating a raising observer from the reader thread and from its sibling observers registered for the same record. Regression tests: `test_dispatch_isolates_a_raising_stopped_callback`, `test_dispatch_isolates_a_raising_notify_callback`, `test_dispatch_isolates_a_raising_console_callback` (`tests/unit/test_debugger_gdb_adapter.py`, a new unit-test file for this module — previously only a real-`gdb` integration test existed).

`gdb_adapter.py::_read_loop` wraps only `parse_mi_line` in `try/except MIParseError`; the subsequent `self._dispatch(record)` call, which invokes every registered `on_stopped`/`on_notify`/`on_console_output` callback directly and synchronously, is completely unguarded. Directly reproduced against a real `gdb --interpreter=mi2` session: registered an `on_stopped` callback that raises `RuntimeError`, hit a real breakpoint, confirmed the reader thread died (`adapter._reader_thread.is_alive() is False`), then sent an unrelated, always-safe follow-up command and confirmed it `TimeoutError`'d after the full configured timeout even though `adapter.is_running` still reports `True` (it only checks `self._process.poll()`, never the reader thread's health). There is no way for a caller to distinguish "GDB is slow" from "the reader thread is permanently dead" other than every future command timing out.

### DebuggerCore-2. `RecursionError` from deeply nested MI values kills the reader thread the same uncaught way as DebuggerCore-1 — HIGH — **[verified]** — **FIXED**

Fixed by adding an instance-level depth counter to `_MIValueParser.parse_value` that raises a clean `MIParseError` once nesting exceeds a new `_MAX_MI_VALUE_DEPTH = 200` constant — comfortably below Python's default recursion limit, far beyond any realistic COBOL data hierarchy's nesting depth, and (unlike a bare `RecursionError`) correctly caught by `_read_loop`'s existing `except MIParseError` guard. Regression tests: `test_deeply_nested_mi_value_raises_mi_parse_error_not_recursion_error`, `test_moderately_nested_mi_value_still_parses` (`tests/unit/test_debugger_mi_protocol.py`).

`_MIValueParser.parse_value`/`parse_tuple`/`parse_list`/`parse_result` recurse once per nested MI tuple/list level with no depth guard. Directly reproduced via binary search on a synthetic deeply-nested-tuple MI line: nesting depth 300 parses fine, depth 332 raises an uncaught `RecursionError` (~3 stack frames consumed per MI nesting level against Python's default 1000-frame limit). Since `RecursionError` isn't a `MIParseError`, `_read_loop`'s guard never catches it, killing the reader thread exactly as in DebuggerCore-1. Real-world trigger likelihood for genuine COBOL/GDB output is unconfirmed — ordinary COBOL group nesting rarely approaches this depth — but the mechanism itself was directly executed, not hypothetical.

### DebuggerCore-3. No explicit `encoding=`/`errors=` on the GDB subprocess's text-mode pipes — a third independent instance of a bug shape this tracker has now found and fixed twice elsewhere — HIGH — **[verified mechanism; not yet observed emitted by real gdb specifically]** — **FIXED**

Fixed by adding `encoding="utf-8", errors="replace"` to the `subprocess.Popen` call in `start()`, the identical fix already applied to Git's own subprocess layer (Git finding #4) and the compiler process layer (Phase 5's CompilerProcess-3) — now a third, previously-independent subprocess invocation in this codebase pinned the same way. Regression test: `test_start_pins_utf8_encoding_on_the_subprocess` (`tests/unit/test_debugger_gdb_adapter.py`), monkeypatching `subprocess.Popen` and asserting the exact kwargs. Re-ran the full real-`gdb` integration suite afterward to confirm the added kwarg doesn't change behavior against a genuine session.

`gdb_adapter.py::GdbAdapter.start()`'s `subprocess.Popen(..., text=True, bufsize=1, ...)` sets no `encoding=`, so decoding falls back to `locale.getpreferredencoding(False)` — confirmed `cp1252` on this machine, identical to the already-fixed Git finding #4 and Phase 5's CompilerProcess-3. Built an isolated repro using the exact `Popen` kwargs shape `gdb_adapter.py` uses, feeding a helper subprocess that writes a byte value `cp1252` cannot decode at all (`0x81`, one of five bytes permanently undefined under that codepage, confirmed via `b'\x81'.decode('cp1252')` raising `UnicodeDecodeError`): the error propagates directly out of the `for raw_line in process.stdout` loop `_read_loop` uses, before the exception guard is even reached — killing the reader thread the same way as DebuggerCore-1/2. Even short of that hard failure, an ordinary non-ASCII byte (e.g. UTF-8 text in a variable value or source path) would silently decode to the wrong characters, mirroring the exact silent-mojibake shape already found for the compiler process layer.

### DebuggerCore-4. `send_command` cannot detect that GDB died while a command was pending; it always blocks for the full configured timeout — MEDIUM — **[verified]** — **FIXED**

Fixed by replacing the single, full-duration `pending.event.wait(...)` with a polling loop that waits in 0.1s increments up to the same total deadline, checking `self.is_running` between polls and raising a specific `GdbNotRunningError` immediately once the process is found dead, instead of waiting out the rest of the original timeout. Regression test: `test_send_command_raises_promptly_when_gdb_dies_while_pending` (`tests/unit/test_debugger_gdb_adapter.py`) — kills a fake process 0.3s into an 8-second timeout and asserts the call returns in well under 2 seconds with `GdbNotRunningError`, not `TimeoutError` after the full wait.

`send_command` checks `self.is_running` only once, before writing the command, then unconditionally waits the full `_command_timeout_seconds`. Directly reproduced: hit a real breakpoint, issued a genuinely slow inferior-call expression, killed the GDB process from a second thread 0.7s into the wait (confirmed `is_running` flipped to `False` at that point) — `send_command` still didn't return until the full 8-second timeout elapsed, wasting ~7.3 seconds reporting a generic timeout instead of a fast, specific "process died" signal.

### DebuggerCore-5. `StoppedEvent.thread_id` has no validation, unlike the near-identical `ThreadInfo.thread_id` for the same domain concept — MEDIUM — **[verified]** — **FIXED**

Fixed by adding a `__post_init__` to `StoppedEvent` that requires `thread_id > 0` when given, matching `ThreadInfo.thread_id`'s existing rule for the identical concept. Regression tests: `test_stopped_event_allows_no_thread_id`, `test_stopped_event_rejects_non_positive_thread_id` (`tests/unit/test_debugger_models.py`).

`ThreadInfo.__post_init__` requires `thread_id > 0`; `StoppedEvent` has no `__post_init__` validation for its own `thread_id: int | None` field representing the identical concept. Verified directly: `StoppedEvent(reason=StopReason.BREAKPOINT_HIT, thread_id=-5)` and `thread_id=0` both construct with no error, while the equivalent `ThreadInfo` construction correctly raises `ValueError`.

### DebuggerCore-6. `StackFrame.function_name` and `ThreadInfo.state` have zero non-empty validation, unlike the structurally identical `Variable.name`/`RegisterValue.name` — LOW/MEDIUM — **[verified]** — **FIXED**

Fixed by adding a non-empty check for `function_name` to `StackFrame.__post_init__` and for `state` to `ThreadInfo.__post_init__`, matching the existing checks on `Variable.name`/`RegisterValue.name`. Regression tests: `test_stack_frame_rejects_empty_function_name`, `test_thread_info_rejects_empty_state` (`tests/unit/test_debugger_models.py`).

`Variable.__post_init__`/`RegisterValue.__post_init__` both reject a blank/whitespace-only required name string; `StackFrame.__post_init__` validates only `level`/`line`, never its own required `function_name`, and `ThreadInfo.__post_init__` validates only `thread_id`, never `state`. Verified directly: `StackFrame(level=0, function_name="")` and `ThreadInfo(thread_id=1, state="")` both construct with the empty string retained verbatim.

### DebuggerCore-7. `Variable.name`/`RegisterValue.name` validate non-emptiness via `.strip()` but never store the normalized value back — LOW — **[verified]** — **FIXED**

### DebuggerCore-8. Empty-string `source_path` passes `Breakpoint`/`StackFrame` validation and silently normalizes to `Path('.')` — LOW/MEDIUM — **[verified]** — **FIXED**

### DebuggerCore-9. The MI c-string parser mishandles GDB's octal escapes for non-printable bytes — MEDIUM — **[verified]** — **FIXED**

Fixed by detecting an octal digit immediately after a backslash in `parse_c_string` and consuming up to 3 octal digits total, decoding the full sequence via `chr(int(octal_digits, 8))` instead of keeping each digit as a literal character. Regression tests: `test_parses_an_octal_escape_in_a_c_string`, `test_parses_a_three_digit_octal_escape_in_a_c_string` (`tests/unit/test_debugger_mi_protocol.py`).

### DebuggerCore-10. A `GdbAdapter` can never be restarted after `terminate()`, with a misleading error message — LOW — **[verified]** — **FIXED**

### DebuggerCore-11. No lock protects `send_command`'s actual `stdin.write()`/`flush()`, only token allocation and the pending-dict insert — LOW — **[plausible, unconfirmed]** — **FIXED**

### DebuggerLogic-1. `read_variable` cannot resolve any WORKING-STORAGE item nested inside a group record — only flat, top-level elementary items work — HIGH — **[reported as directly reproduced]** — **FIXED (for numeric group members; alphanumeric members remain a real, unfixable-via-parsing gap — see below)**

Fixed by adding a second regex, `_FIELD_DECLARATION_PATTERN`, to `gnucobol_symbols.py`, matching the `static cob_field <var> = {size, buffer[+ offset], &attr}; /* NAME */` shape a nested elementary item gets instead of its own dedicated buffer. The offset (when present) is folded directly into the stored `buffer_variable` string as a GDB-evaluable expression (`"b_17+3"`, no spaces — MI commands are whitespace-delimited) rather than adding a new field to `GeneratedFieldSymbol`, since `service.py` already just interpolates that string straight into a `-data-read-memory-bytes` command and GDB's own expression evaluator understands `buffer+N` pointer arithmetic directly, matching exactly how `cobc`'s generated C itself computes the field's address. Verified against real `cobc 3.2.0` output across one, two, and three levels of group nesting: every level's offset is always flattened back to the single outermost buffer directly (never through an intermediate group's own symbol), so this one pattern recovers a nested item regardless of nesting depth. This closes the fix for any nested item GnuCOBOL actually emits a `cob_field` for — confirmed by real compiles to include COMP-3 and plain DISPLAY numeric items — but a plain alphanumeric (`PIC X`) item nested in a group gets neither a buffer nor a `cob_field` at all in `cobc`'s own debug output, so that specific sub-case remains genuinely unrecoverable by any static-parsing approach, not just this one. Regression tests: `test_parse_generated_symbol_map_recovers_a_group_member_at_offset_zero`, `test_parse_generated_symbol_map_recovers_a_group_member_at_a_nonzero_offset`, `test_parse_generated_symbol_map_does_not_confuse_group_and_members` (`tests/unit/test_debugger_gnucobol_symbols.py`, using a real `cobc`-generated header fixture) and `test_debugger_reads_a_group_nested_field_and_a_redefines_view` (`tests/integration/test_gnucobol_variable_decoding.py`) — a genuine end-to-end real-`cobc`/real-`gdb` proof that `DebuggerService.read_variable("CUST-AMOUNT")`/`("CUST-BALANCE")` now return the correct decoded values for two sibling fields in one group.

`gnucobol_symbols.py`'s `_BUFFER_DECLARATION_PATTERN` only matches a `static cob_u8_t <buf>[<size>] ... /* NAME */` declaration. Compiling a real two-field group (`01 CUSTOMER-REC. 05 CUST-AMOUNT ... 05 CUST-NAME ...`) with real `cobc 3.2.0` shows GnuCOBOL gives the *group* its own buffer but represents each subordinate elementary field only as a `cob_field f_N = {size, group_buffer + offset, &attr}; /* FIELD-NAME */` — a construct the regex never matches at all. Directly reproduced end-to-end: `DebuggerService.read_variable("CUST-AMOUNT")` against a real `-g -debug` build raises `DebuggerServiceError: 'CUST-AMOUNT' has no known memory location (was it compiled with cobc -g -debug?)` even though it was, and the field is perfectly ordinary COBOL — the error message actively misattributes the cause. Since virtually every non-toy COBOL program organizes WORKING-STORAGE into records, this materially limits the debugger's headline feature; every existing test fixture across all five debugger test files uses only flat, ungrouped `01` items, which is exactly why this went unnoticed.

### DebuggerLogic-4. LINKAGE SECTION (`CALL ... USING`) parameters are entirely invisible to the symbol map — HIGH — **[reported as directly reproduced]** — **DEFERRED**

Traced every raw `-exec-step` across a real `CALL "CALLEE"` boundary (compiled as a separate dynamically-loaded module, the normal GnuCOBOL-on-Windows shape): it took 19 raw steps just to reach the callee's `PROCEDURE DIVISION` header line — not even a real statement yet — still within the 50-step budget. ### DebuggerLogic-7. `_smart_step`'s suspend/resume of stopped-callbacks around its timeout wait has a narrow race window — LOW/MEDIUM — **[plausible, unconfirmed]** — **DEFERRED**

Not fixed. A correct fix needs cross-thread operation-ID synchronization between the reader thread's callback dispatch and the smart-step timeout path — e.g. a monotonically increasing "attempt ID" that `_handle_stopped` captures and compares against under a lock shared with `_smart_step`'s own timeout-and-reset logic, so a stray late notification from an abandoned internal step can be distinguished from a genuinely new one, rather than the current single shared boolean flag that both sides race on. A cheaper partial mitigation (e.g. a generation counter that only helps when a *new* smart-step starts before the old one's callback fires) doesn't actually close the specific window this finding describes, and a naive "never reset the suspend flag on timeout" fix would be strictly worse — it would silently stop all future callbacks from firing at all, forever, after a single timeout, rather than occasionally firing one extra callback for an abandoned step. This is a genuine synchronization redesign, not a scoped bug patch, and matches this finding's own confidence tag: even the original audit, with real GDB execution available, couldn't force a concrete repro of the race actually manifesting — it requires a step to time out *and* GDB's real response to land within a razor-thin window immediately after, deliberately forcing which is beyond what a reasonable test harness for this pass could justify.

`_suspend_stopped_callbacks` is set `True` for the whole internal step loop and reset to `False` in a `finally` block. ### DebugGUI-3. `collect_local_variables`/`evaluate_watch_expressions` only catch `DebuggerServiceError`, letting a `GdbAdapterError`/`GdbNotRunningError`/`TimeoutError` from `read_variable` escape uncaught and abort the rest of that stop's panel refresh — HIGH — **[verified]** — **FIXED**

Regression tests: `test_collect_local_variables_skips_items_that_raise_an_adapter_error`, `test_evaluate_watch_expressions_falls_back_after_an_adapter_error` (`tests/unit/test_gui_debug_commands.py`), each using a fake service that raises `GdbNotRunningError` specifically (not `DebuggerServiceError`) to prove the widened catch.

### DebugGUI-4. `DebugSessionController.sync_breakpoints()` raises instead of no-op'ing when called with no active session — LOW/MEDIUM — **[verified]** — **FIXED**

### DebugGUI-5. Start Debugging can silently compile and debug stale on-disk source if the pre-flight save fails — MEDIUM — **[confirmed]** — **FIXED**

## Cross-cutting observations (Phase 6)

- **The debugger's core value proposition — reading a live COBOL variable's decoded value by name — was verified end-to-end only against flat data items when originally built, and that's exactly the blind spot that let DebuggerLogic-1/2/3/4 ship**: every one of the four data-shape findings (groups, OCCURS, REDEFINES, LINKAGE) stems from the identical root cause (`gnucobol_symbols.py`'s comment-scraping approach only recognizes one specific `cob_u8_t` buffer-declaration shape) and was only found by compiling COBOL that actually uses these extremely common language constructs — something no existing test fixture across the whole debugger test suite does.
- **This phase independently reproduces the exact "unpinned subprocess encoding" bug shape this tracker has now found and fixed twice already** (Git finding #4, Phase 5's CompilerProcess-3) — a third time, in `gdb_adapter.py`'s GDB subprocess pipes (DebuggerCore-3). Three independent subprocess-invocation call sites in this codebase have now each needed the identical fix; a shared, already-hardened subprocess helper would prevent a fourth recurrence.
- **A single, narrow class of bug — an uncaught exception from a background thread or a sibling-but-different exception type slipping past a narrower `except` clause — recurs across all three Phase 6 subsystems** in different guises: a raising observer callback kills the reader thread (DebuggerCore-1/2), a `GdbAdapterError` leaks past `DebuggerServiceError`-only catches (DebuggerLogic-6), and the identical mismatch breaks the Debug GUI's own panel-refresh error handling (DebugGUI-3). All three are instances of "the exception-handling boundary was drawn one layer too narrow," not three unrelated bugs.
- **Stale-state-after-session-end (DebugGUI-1/2) is the debugger's own instance of a bug shape this tracker has now found and fixed for Bookmarks/Breakpoints (Phase 3, Editor §9) and re-found for Find Results (Phase 7, SearchOutlineTasks-1, below)**: a panel that renders "the current state of something" needs an explicit, complete teardown hook wired to every way that something can end, not just the happy path — and the debugger's own teardown (`_clear_debug_panels`) is itself incomplete (misses Memory) even where a hook does exist.

### UIBootstrap-2. `ThemeService` construction in `create_main_window()` is unguarded — a syntactically valid `settings.json` with an unregistered theme ID crashes the whole app launch — HIGH — **[reported as directly reproduced]**

`ThemeService(registry=create_builtin_theme_registry(), initial_theme_id=...)` calls `ThemeRegistry.get()` eagerly inside `ThemeService.__init__`, raising `ThemeNotFoundError` for any unregistered ID. `ThemeSettings.__post_init__` only validates `active_theme_id` as a non-empty string — it has no knowledge of the Qt-only theme registry — so a stale ID (a removed built-in theme, hand-edited JSON) loads through the settings layer with no error and only crashes later, uncaught, in `application.py`. **FIXED** (code + test). `create_main_window()` now resolves the persisted theme ID against the registry itself first, exactly mirroring the codebase's own established pattern for every comparable resolution in this file: `_builtin_theme_registry.get(_persisted_theme_id)` inside a `try`/`except ThemeNotFoundError`, falling back to `DEFAULT_THEME_ID` on a miss, before `ThemeService` is ever constructed. Test: `test_theme_service_falls_back_to_default_theme_for_an_unknown_persisted_theme_id` in [test_gui_application.py](tests/unit/test_gui_application.py) reproduces the exact original repro (`update_theme(ThemeSettings(active_theme_id="stale-removed-theme"))` then `create_main_window(...)`) and asserts the window now launches successfully with `window._theme_service.active_theme.theme_id == DEFAULT_THEME_ID` instead of raising.

### UIShell-1. Every View-menu tool-window toggle command updates domain state but never touches the real `QDockWidget` — HIGH — **[verified]**

### UIShell-2. Every submenu contribution leaks a new `QMenu`/`QAction`/signal-connection object on every single parent-menu open, unbounded — HIGH — **[verified]**

The submenu branch of `populate_menu` (`command_menus.py`) calls `menu.addMenu(...)`, creating a brand-new `QMenu` every time `populate_menu` runs — which happens on every real menu open via the `aboutToShow` connection. `menu.clear()` does not destroy the previously-created submenu `QMenu` (it's a `QObject` child of the parent, not merely a value in `actions()`), so the old instance becomes unreachable but is never deleted. This is a real, always-triggered path: the built-in File menu registers a real submenu contribution ("File > New"). Directly reproduced: emitted `aboutToShow` on a menu with a submenu contribution 5 times, then 20 more, counting `menu.findChildren(QMenu)` with `processEvents()` interleaved to rule out deferred-deletion delay — growth was exactly 1 leaked `QMenu` (plus its internal `QAction` and `aboutToShow` closure) per open, unbounded, never reclaimed. Plain (non-submenu) command actions do not leak — `QAction` child count stayed constant across 1 through 200 re-opens, and a triggered handler fired exactly once regardless of prior reopen count.

**FIXED** (code + test). `populate_menu` in [command_menus.py](src/opencobol2/gui/command_menus.py) now explicitly finds every direct-child `QMenu` of the menu being repopulated (`menu.findChildren(QMenu, options=Qt.FindChildOption.FindDirectChildrenOnly)`) and calls `.deleteLater()` on each, *before* `menu.clear()` runs — reclaiming exactly the object `clear()` itself never touches. Nested descendants (a submenu's own submenu) need no separate handling: Qt destroys a QObject's children recursively once its own direct parent is deleted. Test: `test_repeated_menu_opens_do_not_leak_submenu_objects` in [test_gui_command_menus.py](tests/unit/test_gui_command_menus.py) reproduces the original finding's own methodology — 20 real `aboutToShow` cycles on a menu with a submenu contribution — then asserts exactly 1 direct-child `QMenu` remains. ### ProjectPanels-5. The terminal's subprocess timeout does not reliably bound the GUI freeze when the command spawns a descendant process — HIGH — **[verified]**

A realistic terminal use (a dev server, a background build, anything piping through an intermediate process) can freeze the whole IDE indefinitely with no indication why the "60-second timeout" never fired.

**DEFERRED**, entangled with ProjectPanels-4 above rather than independently scoped: this finding's severity specifically comes from the freeze happening *on the GUI thread* — a correct standalone fix (killing the whole descendant process tree, e.g. `taskkill /T /F` on Windows, before the final drain, rather than only the direct child) is a real, scoped, independently-doable patch to the subprocess-invocation logic itself, but landing it *inside* `run_command` while that method still executes synchronously on the GUI thread would mean re-verifying a HIGH-severity GUI-freeze fix against a test suite that's about to be rewritten anyway once ProjectPanels-4's background-thread rewrite happens — double work for a fix that would need re-verifying afterward regardless. Test: `test_closing_a_project_clears_stale_find_results` in [test_gui_application.py](tests/unit/test_gui_application.py) reproduces the exact original repro (Find in Files via the real menu action, then Close Project via the real menu action) and asserts the panel is now empty afterward.

### SearchOutlineTasks-2. Find Results and Task List rows carry frozen line/column positions that silently go wrong after the file is edited — MEDIUM — **[verified]**

Neither result type is re-validated or re-computed after being set; both panels are deliberately point-in-time snapshots. Directly reproduced for both: searched/scanned a file, then edited it on disk to shift the real line number of the match/tag without re-searching — the stale row still reported the old line number. Double-clicking a stale row navigates to the wrong line/content with no indication anything is off (an out-of-range stale line degrades to a silent no-op rather than a crash, but an in-range stale line silently lands on the wrong content). The Outline panel does not share this gap, since its refresh is wired directly to live edit signals rather than being a point-in-time snapshot.

**DEFERRED.** This is the documented, deliberate design shape of both panels, not an oversight — they are "point-in-time snapshot" results by construction, same as e.g. a `grep` output would be. A real fix means one of: (a) re-validating/re-resolving each row's position against the file's *current* content before every navigation (its own non-trivial diffing/anchoring problem — the file may have been edited in ways that make the original match text no longer findable at all, not just shifted by a line count), or (b) tying both panels to the same live-edit-signal architecture Outline already uses, which for Find Results specifically would mean either re-running the whole search on every keystroke of every open file (a strictly worse version of SearchOutlineTasks-3) or building real per-match position tracking through `QTextDocument`'s own edit-tracking primitives. Either direction is a genuine feature build, not a scoped patch to the two rows' models. Left as a known, documented limitation rather than shipped half-verified.

### SearchOutlineTasks-3. Outline panel re-lexes and re-parses the entire active document synchronously on every keystroke, with measurable real cost scaling with file size — LOW/MEDIUM — **[verified]**

Every `textChanged` on the active tab triggers a full `tokenize_cobol_source` + `parse_cobol_tokens` pass on the Qt GUI thread with no debounce. Measured directly: a synthetic ~1,500-line COBOL file averaged 26ms per outline computation; a ~6,000-line file (not unrealistic for real COBOL) averaged 107ms — over 100ms of GUI-thread blocking per keystroke while that tab is active. Same root-cause shape as the already-catalogued, deferred CompilerProcess-5, just for outline refresh instead of compilation. Not a correctness bug — the outline itself stays accurate — but real, typing-blocking latency on large files.

**DEFERRED**, and investigated further before settling on that: a plain debounce (a `QTimer` restarted on every keystroke, only recomputing once typing pauses — the same coalescing idiom `syntax_highlighter.py` already uses elsewhere in this codebase) looked at first like a clean scoped patch, but `EditorTabsWidget.active_document_changed` is the one signal both a keystroke edit *and* a plain tab switch fire through (`_handle_active_editor_text_changed` and the `currentChanged` handler both emit it); debouncing that signal uniformly would also delay the outline on an ordinary tab switch, which isn't broken today and has 4 passing tests (`test_outline_populates_when_a_cobol_file_is_opened`, `test_outline_refreshes_when_switching_tabs`, `test_outline_clears_when_the_last_tab_closes`, `test_double_clicking_an_outline_entry_moves_the_editor_cursor`) that assert the outline updates synchronously. Splitting "keystroke-triggered" from "tab-switch-triggered" refresh cleanly needs a second, more specific signal threaded through `EditorTabsWidget` — a real (if modest) API change, not a one-line patch — and even with debouncing in place, a single large-file recompute still eventually costs the same 100ms+ GUI-thread block once the pause fires, so the deeper fix is the same shape as CompilerProcess-5 (move the computation off the GUI thread entirely) rather than merely delaying when it runs on it. Left as-is rather than shipped as a half-measure that only debounces two of the four affected tests' scenarios.

**Checked and found correct:** the outline's "same-tab-only edit guard" works correctly — a background tab's programmatic text mutation does not trigger a refresh, only the active tab's edits do, verified directly and consistent with the existing passing test; unlike Bookmarks/Breakpoints pre-Phase-3-fix, Outline's refresh is wired directly to signals Qt already fires correctly, so it never inherited that bug shape. Closing the only/active tab correctly clears the Outline panel with no dedicated fix needed. Outline never crashes on an empty or genuinely unparseable file, verified directly against garbage/truncated input. A TODO tag inside a string literal is correctly excluded and a genuine comment TODO is correctly kept, mechanically guaranteed since the scan filters to real lexer COMMENT tokens before the regex ever runs. The View menu's checked state for Find Results correctly reflects a forced-visible dock even though `_reveal_find_results()` bypasses the normal service-activation path — verified directly that the bypass's manual `setVisible(True)` still round-trips through the existing dock→service listener.

**Test coverage gaps:** the SearchOutlineTasks-1 gap (no test exercising Close Project's effect on Find Results) is now closed — see its FIXED tag above. No test exercises editing a file after a search/scan and then double-clicking the now-stale row — still open, since SearchOutlineTasks-2 is deferred by design, not fixed. No performance regression test exists for SearchOutlineTasks-3, also still open for the same reason. Executed for real: the full suite (1785 tests passing after this sweep, up from 1784 at the end of GitPanels — the one new test closes SearchOutlineTasks-1's gap).

## Dialogs (`gui/command_palette.py`, `compiler_profiles_dialog.py`, `settings_dialog.py`, `welcome_page.py`)

### Dialogs-1. A malformed STRING_MAP entry (or any field-kind parse error) raised inside `_commit_current_profile_from_form` is never caught — it silently desyncs the dialog on row-switch and defeats the Save button entirely — HIGH — **[reported as directly reproduced]**

`_commit_current_profile_from_form` builds `configuration` from `_read_field_value` and reconstructs the `CompilerProfile` via `dataclasses.replace(...)` with no try/except anywhere in the call chain, in any of its five callers. A STRING_MAP field whose text includes a bare `=value` line (no key) passes `_read_field_value` cleanly (producing `{"": "value", ...}`, see Dialogs-2) but `replace()`'s re-validation raises `ValueError: Compiler configuration object key must not be empty.` two calls later. Directly reproduced two ways with a synthetic STRING_MAP provider driven through a real dialog: (1) **row-switch path** — switching rows with malformed text left in the previously-selected row's widget triggers the uncaught error inside the selection-changed handler, aborting it partway through, so the widget's visible selection and the dialog's internal `_active_row` tracking desync — any further edit the user makes now silently lands in the wrong profile; (2) **Save/OK path** — the identical error is the unguarded first line of `_apply_and_accept`, entirely outside that method's own `try/except (TypeError, ValueError)` around persistence, so the dialog never calls `accept()` and, from the user's perspective, clicking OK does nothing at all, with no error and no explanation. The identical root cause also reproduces for INTEGER_LIST fields (non-numeric text raises an uncaught `ValueError` from a bare `int(token)` call) — this is a systemic gap in the commit path, not STRING_MAP-specific, but STRING_MAP is the only kind where a well-formed-*looking* value (an empty key) sails through the dialog's own read step with zero red flags before blowing up two calls later.

**FIXED** (code + test). `_commit_current_profile_from_form` in [compiler_profiles_dialog.py](src/opencobol2/gui/compiler_profiles_dialog.py) now wraps its own body in `try`/`except (TypeError, ValueError)`, shows one `QMessageBox.critical` on failure, and returns a `bool` instead of `None` so every one of its four callers (`_on_selection_changed`, `_add_profile`, `_set_selected_as_default`, `_apply_and_accept`) can abort its own action on a `False` return without touching `_active_row` or the form — centralizing the error-display logic in one place rather than duplicating it. `_on_selection_changed` specifically reverts the list widget's visible selection back to the row that failed (with signals blocked, so it doesn't re-trigger a commit) *without* reloading the form, so the user's malformed text stays visible and editable rather than being wiped by a reload from the last-known-good state — this is what actually fixes the desync, not just the crash. Test: two new dialog-level tests reproduce both original repros (`test_malformed_string_map_on_row_switch_shows_error_and_keeps_selection`, `test_malformed_integer_list_blocks_apply_and_accept_with_an_error`) in [test_gui_compiler_profiles_dialog.py](tests/unit/test_gui_compiler_profiles_dialog.py), the latter using the real `CustomLocalCompilerProvider`'s own `success_return_codes` INTEGER_LIST field.

### Dialogs-2. STRING_MAP duplicate keys are silently collapsed with no rejection and no warning — earlier value is lost — MEDIUM — **[verified]**

`_read_field_value`'s STRING_MAP branch assigns into a dict per line with no duplicate-key check, so a second `KEY=...` line simply overwrites the first — the duplicate has already vanished before any downstream validation layer could ever detect it happened. Directly reproduced: entered `"DEBUG=1\nDEBUG=0\nRELEASE=1"` — the result was `{"DEBUG": "0", "RELEASE": "1"}`, with `DEBUG=1` silently gone. This confirms the tracker's own "STRING_MAP untested at this layer" note hides a real, quiet data-loss bug, distinct from Dialogs-1's crash — this path never raises at all, it just discards user input. A line with no `=` at all is also silently accepted as a key mapped to an empty value, with zero feedback.

**FIXED** (code + test). `_read_field_value`'s STRING_MAP branch now rejects both shapes explicitly with a clear `ValueError` naming the field and the offending line/key, rather than silently losing data (duplicate key) or waiting for a downstream layer to eventually catch it two calls later with a much less specific message (empty key — the same code path also closes half of Dialogs-1). The error surfaces to the user via the same `_commit_current_profile_from_form` handling Dialogs-1 just added. Test: `test_string_map_field_rejects_a_duplicate_key` and `test_string_map_field_rejects_an_entry_with_no_key` in [test_gui_compiler_profiles_dialog.py](tests/unit/test_gui_compiler_profiles_dialog.py) reproduce the exact original repro (`"DEBUG=1\nDEBUG=0\nRELEASE=1"`) and the empty-key case, asserting `_read_field_value` now raises instead of silently discarding data.

### Dialogs-3. `SettingsDialog._apply_and_accept` has no try/except across its four sequential `update_*` calls, so a failure partway through leaves earlier categories already persisted with no rollback and no error shown — MEDIUM — **[verified]**

The four `update_editor`/`update_cobol`/`update_theme`/`update_external_tools` calls run back-to-back with zero exception handling, unlike the sibling `CompilerProfilesDialog._apply_and_accept`, which validates first and wraps persistence in a proper try/except plus a critical dialog. Since each call independently persists-and-applies with no batching/transaction across the four, a later call's failure leaves everything already applied before it committed to disk. Directly reproduced: constructed the dialog with a genuinely empty theme registry (so the theme combo returns `None`, and the third `update_*` call raises `TypeError`), having first changed the font family/size — the `TypeError` propagated uncaught, the dialog never closed, yet reloading settings from disk afterward showed the font changes already persisted. The one production call site always supplies a non-empty registry, so this exact trigger is dormant in shipped code today — but nothing in the dialog's own construction or apply method enforces or defends that invariant, mirroring this tracker's established "not reachable via current callers, but a real latent gap" pattern.

**FIXED** (code + test). Restructured `_apply_and_accept` in [settings_dialog.py](src/opencobol2/gui/settings_dialog.py) to mirror `CompilerProfilesDialog._apply_and_accept`'s existing validate-then-persist shape exactly: all four settings objects (`EditorSettings`/`CobolSettings`/`ThemeSettings`/`ExternalToolSettings`) are now constructed inside one `try`/`except (TypeError, ValueError)` block *before* any `update_*` call runs; only if all four construct successfully does persistence begin. A failure now shows one `QMessageBox.critical` and leaves every category untouched — there is no window anymore where some categories are on disk and others aren't, since construction failing means none of the four `update_*` calls have run yet. Test: `test_apply_and_accept_persists_nothing_when_a_later_section_fails_to_construct` in [test_gui_settings_dialog.py](tests/unit/test_gui_settings_dialog.py) reproduces the exact original repro (a genuinely empty `ThemeRegistry()`, font family changed first) and asserts the font change is no longer persisted to disk.

## Cross-cutting observations (Phase 7)

- **`gui/application.py` is this phase's single riskiest file by construction, not by any one bug**: at 1278 lines wiring together every service, command handler, and signal connection in the app, it's exactly the kind of file where an omission (a command never wired, a widget never included in a refresh cycle) is invisible until specifically hunted for — three of this phase's seven subsystem reviews (UIBootstrap directly, plus ProjectPanels-2/3 and SearchOutlineTasks-1, both about `_on_project_changed`'s refresh list being incomplete) independently converged on "this file's wiring omits something," not three unrelated bugs.
- **The dock-manager/tool-window-service sync gap (UIShell-1) is the single highest-leverage fix in this entire phase**: it silently breaks 15 of 17 tool windows' View-menu toggle for any panel that starts hidden, and the codebase already contains its own hand-rolled one-off workaround (`_reveal_find_results`) with a comment explicitly describing the general gap — the fix belongs in `ToolWindowDockManager` once, not patched per-panel again.
- **Uncaught, wrong-type, or entirely absent exception handling around a GUI-triggered service call is this phase's single most common defect shape**, occurring independently in at least six of the seven subsystems reviewed: Compiler Profiles' commit path (Dialogs-1), Git's ref-name validation (GitPanels-1) and vanished-repository handling (GitPanels-2) and stage/unstage handlers (GitPanels-3), and is the same root shape already catalogued for the debugger in Phase 6's cross-cutting notes. None of these six is a security concern — each is an ordinary, plausible user action (a branch name, a malformed config field, a deleted file) crashing or silently misbehaving instead of showing a clear, contained error.
- **This phase independently reproduces the "process timeout doesn't bound the actual freeze" gap already flagged as unconfirmed for Phase 2's task/launch-config execution (finding #8)**, now fully reproduced in the Terminal panel (ProjectPanels-5) with a concrete 2-second-configured/120-second-actual freeze — confirming that finding's suspicion was correct and the risk is real, not merely theoretical, anywhere in this codebase that shells out through an intermediate process.
